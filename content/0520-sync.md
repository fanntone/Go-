## 為什麼需要鎖

Go 的口號是「用通訊來共享記憶體，而不是用共享記憶體來通訊」。但這不表示 channel 是萬用解——**保護一小塊共享狀態時，mutex 通常更簡單也更快**。

判斷準則：

| 情境 | 建議 |
| --- | --- |
| 保護一個 struct 的欄位 | `sync.Mutex` |
| 讀多寫少的共享資料 | `sync.RWMutex` |
| 單一計數器或旗標 | `sync/atomic` |
| 在 goroutine 之間**傳遞資料所有權** | channel |
| 協調工作流程、pipeline | channel |
| 等待一組 goroutine 完成 | `sync.WaitGroup` / `errgroup` |
| 只執行一次的初始化 | `sync.Once` |

## `sync.Mutex`

### 結構

```go
type Mutex struct {
	_ noCopy
	mu isync.Mutex  // Go 1.24 起實作搬到 internal/sync
}
```

實際的狀態是一個 `int32`，位元拆成四個部分：

| 位元 | 名稱 | 意義 |
| --- | --- | --- |
| 0 | `mutexLocked` | 是否已被鎖住 |
| 1 | `mutexWoken` | 有 goroutine 被喚醒中，不要再喚醒別人 |
| 2 | `mutexStarving` | 是否處於飢餓模式 |
| 3–31 | `waiterCount` | 等待中的 goroutine 數量 |

### 兩種模式

這是 `sync.Mutex` 設計上最巧妙的地方。

### 自旋的條件

進入等待佇列前，`Lock` 會嘗試「自旋」——不休眠，忙碌等待幾個 CPU 週期。這只在下列條件全部成立時發生：

1. 自旋次數還沒超過 4 次
2. 多核心機器（`GOMAXPROCS > 1`）
3. 至少有一個其他的 P 處於執行狀態
4. 目前 P 的本地執行佇列是空的（沒有別的工作可做）
5. 鎖處於正常模式

理由：如果持鎖者很快就會釋放（常見情況），自旋比「休眠 + 喚醒」便宜得多。但如果沒有其他核心在跑，自旋就是純粹浪費——持鎖者根本沒機會執行。

### 使用注意事項

```go
package main

import (
	"fmt"
	"sync"
)

type Counter struct {
	mu sync.Mutex // ✓ 放在被保護欄位的正上方，慣例上表示保護範圍
	n  int
}

func (c *Counter) Inc() {
	c.mu.Lock()
	defer c.mu.Unlock()
	c.n++
}

func (c *Counter) Value() int {
	c.mu.Lock()
	defer c.mu.Unlock()
	return c.n
}

func main() {
	c := &Counter{} // ✓ 用指標，避免複製
	var wg sync.WaitGroup
	for range 1000 {
		wg.Add(1)
		go func() { defer wg.Done(); c.Inc() }()
	}
	wg.Wait()
	fmt.Println(c.Value()) // 1000
}
```

!!! danger "Mutex 絕對不能複製"
    ```go
    // ✗ 複製了鎖的狀態
    func (c Counter) Bad() { // 值接收者！
        c.mu.Lock()          // 鎖的是複本
        defer c.mu.Unlock()
    }
    ```

    `sync.Mutex` 內含 `noCopy` 標記，`go vet` 會抓到：

    ```text
    ./main.go:12:6: Bad passes lock by value: main.Counter contains sync.Mutex
    ```

    **含有 mutex 的 struct，所有方法都必須用指標接收者。** 這也連帶表示這種 struct 不該被當成 map 的值型別（`m[k].Inc()` 會取到複本）。

!!! warning "Mutex 不可重入（non-reentrant）"
    ```go
    func (c *Counter) IncTwice() {
        c.mu.Lock()
        defer c.mu.Unlock()
        c.Inc() // ✗ 死結！Inc 也會嘗試 Lock
    }
    ```

    Go 刻意不支援可重入鎖。理由是：可重入鎖會讓「這段程式碼持有哪些鎖」變得難以推理，反而更容易寫出死結。

    正確做法是把不加鎖的版本抽出來：

    ```go
    func (c *Counter) Inc() {
        c.mu.Lock()
        defer c.mu.Unlock()
        c.incLocked()
    }

    func (c *Counter) IncTwice() {
        c.mu.Lock()
        defer c.mu.Unlock()
        c.incLocked()
        c.incLocked()
    }

    // 慣例：Locked 後綴表示「呼叫者必須已持有鎖」
    func (c *Counter) incLocked() { c.n++ }
    ```

## `sync.RWMutex`

允許多個讀取者同時持有，但寫入者獨佔。

```go
package main

import (
	"fmt"
	"sync"
)

type Cache struct {
	mu sync.RWMutex
	m  map[string]string
}

func (c *Cache) Get(k string) (string, bool) {
	c.mu.RLock()         // 讀鎖：可以有很多個
	defer c.mu.RUnlock()
	v, ok := c.m[k]
	return v, ok
}

func (c *Cache) Set(k, v string) {
	c.mu.Lock()          // 寫鎖：獨佔
	defer c.mu.Unlock()
	if c.m == nil {
		c.m = map[string]string{}
	}
	c.m[k] = v
}

func main() {
	c := &Cache{}
	c.Set("a", "1")
	fmt.Println(c.Get("a"))
}
```

### 寫入者優先

`RWMutex` 的關鍵設計：**一旦有寫入者在等待，新的讀取者就會被阻塞**。

沒有這個機制的話，持續不斷的讀取請求會讓寫入者永遠等不到機會（寫入者飢餓）。

!!! warning "RWMutex 的讀鎖不可重入"
    ```go
    c.mu.RLock()
    defer c.mu.RUnlock()
    c.someMethodThatAlsoRLocks() // ✗ 可能死結
    ```

    如果在兩次 `RLock` 之間有寫入者提出請求，第二次 `RLock` 會被擋住，而第一次的 `RUnlock` 又還沒執行——死結。

## `sync.WaitGroup`

等待一組 goroutine 完成。

```go
package main

import (
	"fmt"
	"sync"
)

func main() {
	var wg sync.WaitGroup
	results := make([]int, 5)

	for i := range 5 {
		wg.Add(1) // ✓ 在 go 之前呼叫
		go func() {
			defer wg.Done() // ✓ 用 defer，確保 panic 也會遞減
			results[i] = i * i
		}()
	}

	wg.Wait()
	fmt.Println(results) // [0 1 4 9 16]
}
```

三條規則：

1. **`Add` 必須在 `go` 之前呼叫。** 放在 goroutine 內部的話，`Wait` 可能在 `Add` 執行前就通過了。
2. **`Done` 用 `defer`。** 否則 panic 會讓 `Wait` 永遠卡住。
3. **不要複製 `WaitGroup`。** 跟 Mutex 一樣，一定要傳指標。

!!! version "Go 1.25：`WaitGroup.Go`"
    Go 1.25 加入了 `wg.Go(f)`，把「Add + go + defer Done」三步合成一步：

    ```go
    var wg sync.WaitGroup
    for i := range 5 {
        wg.Go(func() {
            results[i] = i * i
        })
    }
    wg.Wait()
    ```

    這消除了忘記 `Add` 或忘記 `Done` 的可能性，建議新程式碼優先使用。

### 需要收集錯誤時用 `errgroup`

```go
package main

import (
	"context"
	"fmt"
	"time"

	"golang.org/x/sync/errgroup"
)

func main() {
	g, ctx := errgroup.WithContext(context.Background())
	g.SetLimit(3) // 最多 3 個並行

	for i := range 10 {
		g.Go(func() error {
			select {
			case <-time.After(10 * time.Millisecond):
				if i == 4 {
					return fmt.Errorf("任務 %d 失敗", i)
				}
				return nil
			case <-ctx.Done():
				return ctx.Err()
			}
		})
	}

	if err := g.Wait(); err != nil {
		fmt.Println("錯誤:", err) // 任務 4 失敗
	}
}
```

`errgroup` 的三個優勢：回傳第一個錯誤、任一失敗自動取消 context、`SetLimit` 控制並行度。

## `sync.Once`

保證某段程式碼只執行一次，而且**所有呼叫者都會等到它執行完**。

```go
package main

import (
	"fmt"
	"sync"
)

var (
	once   sync.Once
	config *Config
)

type Config struct{ Value string }

func GetConfig() *Config {
	once.Do(func() {
		fmt.Println("初始化中…（只會印一次）")
		config = &Config{Value: "loaded"}
	})
	return config
}

func main() {
	var wg sync.WaitGroup
	for range 5 {
		wg.Add(1)
		go func() { defer wg.Done(); _ = GetConfig() }()
	}
	wg.Wait()
	fmt.Println(GetConfig().Value)
}
```

### 實作要點

```go
type Once struct {
	done atomic.Uint32
	m    Mutex
}

func (o *Once) Do(f func()) {
	if o.done.Load() == 0 {   // 快路徑：一次原子讀取
		o.doSlow(f)
	}
}

func (o *Once) doSlow(f func()) {
	o.m.Lock()
	defer o.m.Unlock()
	if o.done.Load() == 0 {   // 雙重檢查
		defer o.done.Store(1) // f 執行完才設定
		f()
	}
}
```

兩個細節值得注意：

- **`done` 在 `f()` 完成後才設定**（用 `defer`）。這保證「`Do` 回傳時，`f` 一定已經跑完」——否則其他 goroutine 可能看到半初始化的狀態。
- **`f` panic 也算「執行過」**。`defer o.done.Store(1)` 在 panic 展開時仍會執行，之後的 `Do` 不會重試。如果需要重試語意，得自己實作。

!!! version "Go 1.21：`OnceFunc`、`OnceValue`、`OnceValues`"
    ```go
    // 更簡潔的寫法
    var getConfig = sync.OnceValue(func() *Config {
        return &Config{Value: "loaded"}
    })

    func main() {
        cfg := getConfig() // 第一次執行，之後回傳快取值
    }
    ```

    `OnceValues` 支援 `(T, error)` 的回傳形式，很適合「只初始化一次但可能失敗」的場景。

## `sync/atomic`

單一變數的無鎖操作。比 mutex 快一個數量級，但只能保護**單一變數**。

!!! version "Go 1.19：型別化的原子型別"
    舊的函式式 API（`atomic.AddInt64(&x, 1)`）容易誤用——很容易忘記某處直接讀寫了 `x`。Go 1.19 加入型別化版本，把不安全的存取從型別系統上排除：

```go
package main

import (
	"fmt"
	"sync"
	"sync/atomic"
)

type Stats struct {
	requests atomic.Int64
	errors   atomic.Int64
	enabled  atomic.Bool
	handler  atomic.Pointer[Handler]
}

type Handler struct{ Name string }

func main() {
	var s Stats
	s.enabled.Store(true)
	s.handler.Store(&Handler{Name: "v1"})

	var wg sync.WaitGroup
	for range 1000 {
		wg.Add(1)
		go func() {
			defer wg.Done()
			s.requests.Add(1)
		}()
	}
	wg.Wait()

	fmt.Println(s.requests.Load())      // 1000
	fmt.Println(s.enabled.Load())       // true
	fmt.Println(s.handler.Load().Name)  // v1

	// CAS：只在目前值符合預期時才更新
	old := s.requests.Load()
	ok := s.requests.CompareAndSwap(old, old+100)
	fmt.Println(ok, s.requests.Load())  // true 1100
}
```

可用型別：`atomic.Int32`、`Int64`、`Uint32`、`Uint64`、`Uintptr`、`Bool`、`Pointer[T]`、`Value`。

### `atomic.Value` 的用途：無鎖設定熱更新

```go
package main

import (
	"fmt"
	"sync/atomic"
)

type Config struct {
	Timeout int
	Retries int
}

var cfg atomic.Pointer[Config]

func Get() *Config { return cfg.Load() }

func Reload(c *Config) { cfg.Store(c) } // 整份替換，讀取端完全無鎖

func main() {
	Reload(&Config{Timeout: 30, Retries: 3})
	fmt.Println(*Get())

	Reload(&Config{Timeout: 60, Retries: 5})
	fmt.Println(*Get())
}
```

**讀取路徑完全沒有鎖**，只有一次原子指標載入。這是高頻讀取設定的最佳模式。關鍵是 `Config` 本身**不可變**——要更新就整份替換，絕不修改既有的那份。

## 記憶體模型與 `-race`

### happens-before

Go 的記憶體模型定義了「一個 goroutine 的寫入，什麼時候保證能被另一個 goroutine 看到」。核心是 **happens-before** 關係：

| 建立 happens-before 的操作 |
| --- |
| `go` 陳述式 happens-before 新 goroutine 開始執行 |
| channel 傳送 happens-before 對應的接收完成 |
| channel 關閉 happens-before 接收到零值 |
| 無緩衝 channel 的接收 happens-before 對應傳送完成 |
| `mu.Unlock()` happens-before 之後的 `mu.Lock()` 回傳 |
| `once.Do(f)` 中 `f` 的完成 happens-before 任何 `Do` 回傳 |
| 原子操作依照 sequential consistency 排序 |

**沒有 happens-before 關係的並行讀寫就是資料競爭（data race），行為未定義。**

```go
package main

// ✗ 典型的資料競爭
var done bool
var msg string

func setup() {
	msg = "hello"
	done = true // 沒有同步 → 另一個 goroutine 可能先看到 done=true 而 msg=""
}

func main() {
	go setup()
	for !done { // 忙碌等待，而且可能永遠看不到 done 變 true
	}
	println(msg)
}
```

編譯器可能把 `for !done {}` 最佳化成 `if !done { for {} }`（因為它看不到任何會改變 `done` 的同步操作），程式就永遠卡住。

正確寫法用 channel 或 atomic：

```go
var done = make(chan struct{})
var msg string

func setup() {
	msg = "hello"
	close(done) // 建立 happens-before
}

func main() {
	go setup()
	<-done
	println(msg) // 保證看到 "hello"
}
```

### 一定要跑 `-race`

```bash
go test -race ./...
go run -race main.go
go build -race -o app-race .
```

競爭偵測器會報告：

```text
WARNING: DATA RACE
Write at 0x00c000112010 by goroutine 7:
  main.setup()
      /tmp/main.go:9 +0x2e

Previous read at 0x00c000112010 by main goroutine:
  main.main()
      /tmp/main.go:14 +0x3c
```

!!! tip "`-race` 的成本與限制"
    - **記憶體用量增加 5–10 倍，速度慢 2–20 倍。** 不要在正式環境長期開啟。
    - **只能偵測「實際發生」的競爭。** 沒被觸發的程式碼路徑不會被檢查——所以測試覆蓋率很重要。
    - **CI 一定要跑。** 這是最划算的投資：資料競爭造成的 bug 極難重現，也極難除錯。

    建議做法：CI 上跑 `go test -race ./...`，正式環境用一般建置。

## 效能對照

| 操作 | 大致成本（無競爭） |
| --- | --- |
| `atomic.Int64.Add` | ~5 ns |
| `atomic.Int64.Load` | ~0.3 ns |
| `Mutex.Lock` + `Unlock` | ~15 ns |
| `RWMutex.RLock` + `RUnlock` | ~20 ns |
| `RWMutex.Lock` + `Unlock` | ~25 ns |
| 無緩衝 channel 收發 | ~150 ns |
| 有緩衝 channel 收發（未滿） | ~50 ns |

有競爭時，數字會急遽惡化——mutex 在高競爭下可能到微秒級，因為涉及 goroutine 休眠與喚醒。

**這張表最重要的訊息**：channel 比 mutex 貴一個數量級。用 channel 傳遞資料所有權、協調流程是對的；用 channel 當互斥鎖（`ch := make(chan struct{}, 1)`）就是繞遠路。

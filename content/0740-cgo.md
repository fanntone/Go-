## cgo 是什麼

cgo 讓 Go 呼叫 C 函式（也讓 C 呼叫 Go）。它不是函式庫，而是**編譯工具鏈的一部分**：`go build` 看到 `import "C"` 就會啟動 cgo，產生膠水程式碼、呼叫系統的 C 編譯器、再把結果連結進來。

```go
package main

/*
#include <stdio.h>
#include <stdlib.h>

int add(int a, int b) {
    return a + b;
}
*/
import "C"

import "fmt"

func main() {
	fmt.Println(C.add(3, 4)) // 7
}
```

注意兩個語法細節：

1. **C 程式碼寫在 `import "C"` **正上方**的註解裡**，中間不能有空行。
2. **`import "C"` 必須單獨一行**，不能跟其他 import 放在同一個 group。

Go 呼叫 C 不是普通的函式呼叫。中間發生了不少事：

    Go 1.26 最佳化了 cgo 呼叫的基礎路徑。對於大量呼叫 C 函式的程式（影像處理、加密、資料庫驅動），這是可觀的改善。

### 實測

```go
package main

/*
static int c_add(int a, int b) { return a + b; }
*/
import "C"

import (
	"fmt"
	"testing"
)

//go:noinline
func goAdd(a, b int) int { return a + b }

func main() {
	r1 := testing.Benchmark(func(b *testing.B) {
		for i := 0; i < b.N; i++ {
			_ = goAdd(3, 4)
		}
	})
	r2 := testing.Benchmark(func(b *testing.B) {
		for i := 0; i < b.N; i++ {
			_ = C.c_add(3, 4)
		}
	})
	fmt.Println("Go :", r1)
	fmt.Println("cgo:", r2)
}
```

典型結果：

```text
Go : 1000000000	         1.8 ns/op
cgo:  35000000	        33.4 ns/op
```

**實務結論：把工作批次化。** 與其呼叫 C 函式一百萬次處理一個元素，不如呼叫一次處理一百萬個元素。

```go
// ✗ 一百萬次 cgo 呼叫，光是開銷就 33 毫秒
for i := range data {
	out[i] = C.process_one(C.int(data[i]))
}

// ✓ 一次呼叫
C.process_batch(
	(*C.int)(unsafe.Pointer(&data[0])),
	(*C.int)(unsafe.Pointer(&out[0])),
	C.int(len(data)),
)
```

## 指標傳遞規則

這是 cgo 最容易出錯的地方。Go 的 GC 會移動堆疊、會回收沒有參照的物件，而 C 對此一無所知。

### 官方規則

**規則一：Go 可以傳指標給 C，但 C 不能在呼叫返回後繼續持有它。**

```go
// ✓ C 函式在執行期間使用這個指標，返回後不再持有
C.process(unsafe.Pointer(&goSlice[0]), C.int(len(goSlice)))

// ✗ C 把指標存起來留著以後用 —— 未定義行為
C.register_callback_data(unsafe.Pointer(&goStruct))
```

**規則二：傳給 C 的 Go 記憶體，本身不能包含指向 Go 記憶體的指標。**

```go
// ✗ 這個 struct 內含指向 Go 記憶體的指標
type Bad struct {
	Name *string  // ← 指向 Go 堆積
	Data []byte   // ← slice 標頭裡有指標
}
C.use(unsafe.Pointer(&Bad{}))

// ✓ 只有值型別
type Good struct {
	ID    C.int
	Value C.double
	Buf   [64]C.char
}
C.use(unsafe.Pointer(&Good{}))
```

### 檢查器

Go 在執行期有一個 cgo 指標檢查器，預設開啟：

```bash
GODEBUG=cgocheck=1 go run main.go   # 預設，基本檢查
GODEBUG=cgocheck=2 go run main.go   # 更嚴格但更慢
```

違規時會直接 panic：

```text
panic: runtime error: cgo argument has Go pointer to unpinned Go pointer
```

!!! version "Go 1.21：`runtime.Pinner`"
    有時候你**確實需要**讓 C 持有 Go 指標一段時間（例如非同步回呼）。Go 1.21 提供了官方支援：

    ```go
    package main

    import (
        "runtime"
        "unsafe"
    )

    func withPinned(data []byte, fn func(unsafe.Pointer)) {
        var pinner runtime.Pinner
        defer pinner.Unpin()

        pinner.Pin(&data[0]) // 固定住，GC 不會移動它
        fn(unsafe.Pointer(&data[0]))
    }
    ```

    被 pin 住的物件在 `Unpin` 之前不會被移動或回收。這比以前那些 `cgo.Handle` 加全域 map 的變通做法安全得多。

    注意 pin 住的物件仍然會被 GC **掃描**，只是不會被移動；而且 pin 太多物件會影響 GC 效率。

### `cgo.Handle`：傳遞 Go 物件給 C 的正確方式

如果 C 需要一個「代表某個 Go 物件」的東西（典型場景是 callback 的使用者資料），用 `cgo.Handle`：

```go
package main

/*
typedef void (*callback_t)(unsigned long long handle);
static void invoke(callback_t cb, unsigned long long h) { cb(h); }
*/
import "C"

import (
	"fmt"
	"runtime/cgo"
)

type Context struct{ Name string }

//export goCallback
func goCallback(h C.ulonglong) {
	ctx := cgo.Handle(h).Value().(*Context)
	fmt.Println("回呼中，context:", ctx.Name)
}

func main() {
	ctx := &Context{Name: "my-context"}

	h := cgo.NewHandle(ctx)
	defer h.Delete() // ✓ 一定要刪除，否則洩漏

	C.invoke(C.callback_t(C.goCallback), C.ulonglong(h))
}
```

`cgo.Handle` 是一個**不透明的整數**，內部對應到一張全域表。C 只看到一個數字，Go 這邊可以安全地把它換回原本的物件。**Go 指標從來沒有離開 Go 的世界。**

## 字串與記憶體管理

```go
package main

/*
#include <stdlib.h>
#include <string.h>

static char* make_greeting(const char* name) {
    size_t n = strlen(name) + 8;
    char* out = malloc(n);
    snprintf(out, n, "Hello, %s", name);
    return out;
}
*/
import "C"

import (
	"fmt"
	"unsafe"
)

func greet(name string) string {
	// Go string → C string（會 malloc 並複製）
	cName := C.CString(name)
	defer C.free(unsafe.Pointer(cName)) // ✓ 必須手動釋放

	cOut := C.make_greeting(cName)
	defer C.free(unsafe.Pointer(cOut)) // ✓ C 端 malloc 的也要釋放

	// C string → Go string（會複製）
	return C.GoString(cOut)
}

func main() {
	fmt.Println(greet("Go"))
}
```

### 轉換函式對照

| 函式 | 方向 | 是否配置 |
| --- | --- | --- |
| `C.CString(s)` | Go string → `*C.char` | **malloc**，必須 `C.free` |
| `C.CBytes(b)` | Go `[]byte` → `unsafe.Pointer` | **malloc**，必須 `C.free` |
| `C.GoString(p)` | `*C.char` → Go string | Go 堆積，GC 管理 |
| `C.GoStringN(p, n)` | 指定長度版本 | 同上 |
| `C.GoBytes(p, n)` | C 記憶體 → Go `[]byte` | 同上 |

!!! danger "`C.CString` 忘記 free 就是記憶體洩漏"
    這塊記憶體是 C 的 `malloc` 配置的，**Go 的 GC 完全不知道它的存在**，永遠不會回收。

    ```go
    // ✗ 每次呼叫洩漏一次
    func bad(s string) {
        C.use(C.CString(s))
    }

    // ✓
    func good(s string) {
        cs := C.CString(s)
        defer C.free(unsafe.Pointer(cs))
        C.use(cs)
    }
    ```

    這種洩漏用 Go 的 pprof **看不到**（它只看 Go 堆積）。要用 valgrind、ASAN 或作業系統層級的工具才能發現。

## cgo 的代價清單

### ① 交叉編譯幾乎無法使用

```bash
# 純 Go：一行搞定
GOOS=linux GOARCH=arm64 go build .

# 有 cgo：需要目標平台的完整 C 交叉編譯工具鏈
CGO_ENABLED=1 GOOS=linux GOARCH=arm64 CC=aarch64-linux-gnu-gcc go build .
```

這是 cgo 最痛的代價。Go「一個指令編出所有平台」的優勢直接消失。

### ② 建置變慢

cgo 要呼叫系統的 C 編譯器，而且**不吃 Go 的建置快取**。有 cgo 的專案編譯時間常常是純 Go 的好幾倍。

### ③ 除錯工具失效

- Go 的 profiler 看不到 C 那邊的堆疊（除非用 `SetCgoTraceback`）
- race detector 看不到 C 的記憶體存取
- delve 在 C 程式碼裡幫不上忙
- C 端的 segfault 會產生難讀的堆疊追蹤

### ④ 每個 cgo 呼叫可能佔用一條執行緒

C 函式無法被 Go 排程器搶佔。長時間執行的 C 呼叫會一直佔著 M。大量並行的 cgo 呼叫會讓執行緒數量膨脹，可能撞到 10000 條的上限而直接 crash。

### ⑤ 靜態連結變複雜

用了 cgo 之後，執行檔預設會動態連結 libc。想放進 `FROM scratch` 的容器映像就需要額外處理：

```bash
CGO_ENABLED=1 go build -ldflags="-extldflags=-static" -tags netgo .
```

而且 glibc 的靜態連結有已知問題（NSS、DNS 解析），通常要改用 musl。

## 什麼時候該用 cgo

**✓ 值得的情況：**

| 場景 | 理由 |
| --- | --- |
| 綁定成熟的 C 函式庫 | SQLite、FFmpeg、OpenCV、libvips —— 重寫不切實際 |
| 需要作業系統的特定 API | 某些系統呼叫沒有 Go 的封裝 |
| 硬體或驅動程式介面 | 廠商只提供 C SDK |
| 極致效能的專用程式碼 | 手寫 SIMD 組合語言 |

**✗ 不值得的情況：**

| 場景 | 替代方案 |
| --- | --- |
| 「C 比較快」 | 呼叫開銷可能抵銷收益。先量測 |
| 有純 Go 的替代品 | `modernc.org/sqlite`（純 Go SQLite）、`image/*` |
| 只是要重用一小段邏輯 | 直接用 Go 重寫 |
| 需要交叉編譯或 scratch 映像 | 成本太高 |

### 純 Go 的替代品越來越多

| C 函式庫 | 純 Go 替代 |
| --- | --- |
| SQLite (`mattn/go-sqlite3`) | `modernc.org/sqlite` |
| libgit2 | `go-git/go-git` |
| zlib | `compress/flate`（標準庫） |
| OpenSSL | `crypto/*`（標準庫） |
| libyaml | `gopkg.in/yaml.v3` |

**如果有可用的純 Go 版本，優先選它。** 效能通常只差一點，但你換回了交叉編譯、快速建置、完整的除錯工具。

## 相關的環境變數

```bash
CGO_ENABLED=0    # 完全停用 cgo（強制純 Go）
CGO_ENABLED=1    # 啟用（有 C 編譯器時的預設值）
CC=clang         # 指定 C 編譯器
CGO_CFLAGS="-O2 -I/usr/local/include"
CGO_LDFLAGS="-L/usr/local/lib -lmylib"
```

!!! tip "在 CI 裡強制 `CGO_ENABLED=0`"
    ```bash
    CGO_ENABLED=0 go build ./...
    ```

    這能在**編譯期**就抓到「不小心引入了需要 cgo 的相依」。有些套件（例如某些 DNS 解析路徑、`os/user`）在有 cgo 時會走 C 實作，關掉後改走純 Go 實作。

    這也順帶讓執行檔完全靜態連結，可以直接放進 `FROM scratch` 映像：

    ```dockerfile
    FROM golang:1.26 AS build
    WORKDIR /src
    COPY . .
    RUN CGO_ENABLED=0 go build -ldflags="-s -w" -o /app .

    FROM scratch
    COPY --from=build /app /app
    ENTRYPOINT ["/app"]
    ```

## 一個完整的範例

包裝一個簡單的 C 函式庫，示範所有正確的做法：

```go
package main

/*
#include <stdlib.h>
#include <string.h>

typedef struct {
    int    width;
    int    height;
    unsigned char* data;
} image_t;

static image_t* image_new(int w, int h) {
    image_t* img = malloc(sizeof(image_t));
    img->width  = w;
    img->height = h;
    img->data   = calloc(w * h, 1);
    return img;
}

static void image_free(image_t* img) {
    if (img) {
        free(img->data);
        free(img);
    }
}

static void image_fill(image_t* img, unsigned char v) {
    memset(img->data, v, img->width * img->height);
}
*/
import "C"

import (
	"errors"
	"fmt"
	"runtime"
	"unsafe"
)

// Image 包裝 C 的 image_t，確保資源被正確釋放
type Image struct {
	ptr *C.image_t
}

func NewImage(w, h int) (*Image, error) {
	if w <= 0 || h <= 0 {
		return nil, errors.New("寬高必須為正數")
	}

	p := C.image_new(C.int(w), C.int(h))
	if p == nil {
		return nil, errors.New("配置失敗")
	}

	img := &Image{ptr: p}

	// 保險：即使呼叫端忘記 Close，GC 時也會釋放
	runtime.AddCleanup(img, func(p *C.image_t) { C.image_free(p) }, p)

	return img, nil
}

func (im *Image) Close() {
	if im.ptr != nil {
		C.image_free(im.ptr)
		im.ptr = nil
	}
}

func (im *Image) Fill(v byte) { C.image_fill(im.ptr, C.uchar(v)) }

// Bytes 回傳一個「借用」C 記憶體的 slice —— 不複製，但 Image 關閉後就失效
func (im *Image) Bytes() []byte {
	n := int(im.ptr.width) * int(im.ptr.height)
	return unsafe.Slice((*byte)(unsafe.Pointer(im.ptr.data)), n)
}

func main() {
	img, err := NewImage(4, 4)
	if err != nil {
		panic(err)
	}
	defer img.Close() // ✓ 明確釋放才是主要手段

	img.Fill(0xAB)
	fmt.Printf("%X\n", img.Bytes()[:8])
}
```

!!! version "Go 1.24：`runtime.AddCleanup` 取代 `SetFinalizer`"
    `runtime.SetFinalizer` 有幾個長期問題：物件復活（resurrection）、循環參照造成永不執行、以及會延長物件生命週期一個 GC 週期。

    Go 1.24 加入 `runtime.AddCleanup`，語意更清楚也更安全：cleanup 函式**不會**收到物件本身的指標（避免復活），可以對同一物件註冊多個，而且不會阻止物件被回收。

    **但兩者都只是保險。** 資源釋放的主要手段永遠是明確的 `Close()` + `defer`——finalizer 何時執行完全不確定，可能永遠不執行（程式結束時不會執行）。

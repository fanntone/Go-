## 伺服器：每連線一個 goroutine

`net/http` 的伺服器模型非常簡單直白：

```text
ListenAndServe():
    ln := net.Listen("tcp", addr)
    for {
        conn := ln.Accept()
        go serve(conn)      ← 每條連線開一個 goroutine
    }

serve(conn):
    for {                   ← keep-alive：同一條連線可處理多個請求
        req := readRequest(conn)
        handler.ServeHTTP(w, req)
        if 不能 keep-alive { break }
    }
    conn.Close()
```

在其他語言裡，「每連線一執行緒」是眾所周知的反模式（C10K 問題）。在 Go 裡它可行，因為：

1. **goroutine 便宜** —— 2 KB 起跳，不是 8 MB。
2. **netpoller 讓阻塞的讀寫不佔用執行緒** —— 見 [網路輪詢器](netpoller.html)。

結果是：你可以用最直覺的同步寫法，得到事件驅動架構的效能。

!!! warning "但這不代表沒有上限"
    每條連線至少消耗：
    - 一個 goroutine（2 KB 起，實際常到 8–16 KB）
    - 讀寫緩衝區（`bufio.Reader` 4 KB + `bufio.Writer` 4 KB）
    - `http.Request` 與相關結構

    **實務上每條閒置連線約 10–30 KB。** 十萬條連線就是 1–3 GB。高連線數的服務仍然需要限流：

    ```go
    import "golang.org/x/net/netutil"

    ln, _ := net.Listen("tcp", ":8080")
    ln = netutil.LimitListener(ln, 10000) // 超過就不 accept
    srv.Serve(ln)
    ```

## 逾時：唯一最重要的設定

**預設的 `http.Server` 沒有任何逾時。** 這是 Go 標準庫少數會讓人踩雷的預設值。

```go
package main

import (
	"net/http"
	"time"
)

func main() {
	mux := http.NewServeMux()

	srv := &http.Server{
		Addr:    ":8080",
		Handler: mux,

		// 讀取請求標頭的最長時間 —— 防 Slowloris 攻擊
		ReadHeaderTimeout: 5 * time.Second,

		// 讀完整個請求（含 body）的最長時間
		ReadTimeout: 30 * time.Second,

		// 從讀完標頭到寫完回應的最長時間
		WriteTimeout: 30 * time.Second,

		// keep-alive 連線的閒置上限
		IdleTimeout: 120 * time.Second,

		// 標頭大小上限（預設 1 MB）
		MaxHeaderBytes: 1 << 20,
	}

	srv.ListenAndServe()
}
```

!!! danger "`WriteTimeout` 與長時間的 handler"
    `WriteTimeout` 包含 handler 的執行時間。如果你有需要跑 5 分鐘的 handler（大檔案下載、SSE、長輪詢），設 30 秒的 `WriteTimeout` 會讓它被截斷。

    對這類 endpoint 的解法：

    ```go
    // 方法一：整個伺服器不設 WriteTimeout，改在每個 handler 用 context 控制
    srv := &http.Server{
        ReadHeaderTimeout: 5 * time.Second,
        // 不設 WriteTimeout
    }

    func normalHandler(w http.ResponseWriter, r *http.Request) {
        ctx, cancel := context.WithTimeout(r.Context(), 30*time.Second)
        defer cancel()
        doWork(ctx)
    }

    // 方法二：用 http.TimeoutHandler 包裝需要限制的路由
    mux.Handle("/api/", http.TimeoutHandler(apiHandler, 30*time.Second, "timeout"))
    ```

## ServeMux：用內建的，還是自己建一個

### 這是什麼

`ServeMux` 是 Go 的**路由器**：把「請求的路徑」對應到「處理它的 handler」。

你會看到兩種啟動寫法，很多人搞不清楚差在哪：

```go
// 寫法 A：最原始的 sample
http.HandleFunc("GET /ok", h)
http.ListenAndServe(":8080", nil)

// 寫法 B：自己建一個
mux := http.NewServeMux()
mux.HandleFunc("GET /ok", h)
http.ListenAndServe(":8080", mux)
```

**路由功能上，兩者完全相同。** `http.HandleFunc` 只是 `http.DefaultServeMux.HandleFunc` 的薄包裝；`ListenAndServe` 的第二個參數傳 `nil` 時，`net/http` 內部會把它換成 `http.DefaultServeMux`。

也就是說，寫法 A 不是「沒用 mux」，而是**用了一個 net/http 幫你建好的全域 mux**。pattern 語法、優先序規則、`{id}` 參數——全部一模一樣。

!!! note "這是 Go 標準庫的固定慣例"
    一旦看懂這個模式，很多套件都是同一回事：**套件層級的便利函式背後都藏著一個全域實例**，同時再提供建構函式讓你自己造。

    | 便利寫法（操作全域） | 明確寫法（自己的實例） |
    | --- | --- |
    | `http.HandleFunc(...)` | `http.NewServeMux()` |
    | `http.Get(url)` | `&http.Client{...}` |
    | `log.Println(...)` | `log.New(...)` |
    | `flag.String(...)` | `flag.NewFlagSet(...)` |
    | `slog.Info(...)` | `slog.New(handler)` |

    左欄存在是為了讓 hello world 只要三行；右欄存在是為了讓正式程式能設定它、替換它、測試時隔離它。看到 `NewXxx()` 出現，通常代表作者從「隨便跑跑」切換到「這要正式用」。

### 該用哪一個

| 情境 | 建議 |
| --- | --- |
| 教學範例、一次性腳本、本機實驗 | 全域寫法，少打幾個字沒差 |
| 任何會上線的服務 | **一律自己建** |
| 需要套中介層 | 自己建（雖然 `Recoverer(http.DefaultServeMux)` 也能動） |
| 需要多個 server（對外 + 內部） | 一定要自己建 |
| 需要寫測試 | 一定要自己建 |

### 實務問題一：第三方套件會偷偷改你的路由表

這是最該知道的一個。`DefaultServeMux` 是全域變數，**任何套件的 `init()` 都能往裡面註冊**，包括你根本沒直接 import 的間接相依。

最有名的是 `net/http/pprof`：

```go
package main

import (
	"fmt"
	"net/http"

	_ "net/http/pprof" // ← 只是匿名 import，一行都沒呼叫
)

func probe(mux *http.ServeMux, paths ...string) {
	for _, p := range paths {
		req, _ := http.NewRequest("GET", "http://example.com"+p, nil)
		if _, pattern := mux.Handler(req); pattern != "" {
			fmt.Printf("   %-24s ⚠ 已註冊 → %s\n", p, pattern)
		} else {
			fmt.Printf("   %-24s 未註冊 (404)\n", p)
		}
	}
}

func main() {
	mine := http.NewServeMux()
	mine.HandleFunc("GET /api/users", func(w http.ResponseWriter, r *http.Request) {})

	paths := []string{"/api/users", "/debug/pprof/", "/debug/pprof/heap"}

	fmt.Println("http.DefaultServeMux ← ListenAndServe(addr, nil) 用的就是它")
	probe(http.DefaultServeMux, paths...)

	fmt.Println("\n自己建的 mux")
	probe(mine, paths...)
}
```

```text
http.DefaultServeMux ← ListenAndServe(addr, nil) 用的就是它
   /api/users               未註冊 (404)
   /debug/pprof/            ⚠ 已註冊 → GET /debug/pprof/
   /debug/pprof/heap        ⚠ 已註冊 → GET /debug/pprof/

自己建的 mux
   /api/users               ⚠ 已註冊 → GET /api/users
   /debug/pprof/            未註冊 (404)
   /debug/pprof/heap        未註冊 (404)
```

**一行匿名 import，公開服務上就多了這些端點：**

| 路徑 | 洩漏什麼 |
| --- | --- |
| `/debug/pprof/heap` | 堆積快照，含記憶體中的資料 |
| `/debug/pprof/goroutine?debug=2` | 所有 goroutine 的完整呼叫堆疊 |
| `/debug/pprof/profile` | 30 秒 CPU 剖析——也能當 DoS 用 |
| `/debug/pprof/cmdline` | 完整命令列參數（常含設定與密鑰） |

`expvar` 也一樣，它會註冊 `/debug/vars`。

**怎麼檢查自己有沒有中招**：把上面那個 `probe` 函式貼進你的專案跑一次就知道。

**怎麼解決**：自己建 mux，並且用**兩個 server**——對外與對內分開，內部那個只綁 `localhost`：

```go
package main

import (
	"log/slog"
	"net/http"
	"net/http/pprof" // ← 非匿名，手動註冊
	"time"
)

func main() {
	// 對外：只有你明確註冊的東西
	api := http.NewServeMux()
	api.HandleFunc("GET /api/users/{id}", getUser)

	public := &http.Server{
		Addr:              ":8080",
		Handler:           api,
		ReadHeaderTimeout: 5 * time.Second,
		IdleTimeout:       120 * time.Second,
	}

	// 對內：pprof 與健康檢查，明確註冊、只綁 localhost
	admin := http.NewServeMux()
	admin.HandleFunc("GET /debug/pprof/", pprof.Index)
	admin.HandleFunc("GET /debug/pprof/profile", pprof.Profile)
	admin.Handle("GET /debug/pprof/heap", pprof.Handler("heap"))
	admin.Handle("GET /debug/pprof/goroutine", pprof.Handler("goroutine"))
	admin.HandleFunc("GET /healthz", func(w http.ResponseWriter, r *http.Request) {
		w.Write([]byte("ok"))
	})

	internal := &http.Server{
		Addr:              "127.0.0.1:6060", // ← 外面連不到
		Handler:           admin,
		ReadHeaderTimeout: 5 * time.Second,
	}

	go func() { slog.Error("internal", "err", internal.ListenAndServe()) }()
	slog.Error("public", "err", public.ListenAndServe())
}

func getUser(w http.ResponseWriter, r *http.Request) {
	w.Write([]byte(r.PathValue("id")))
}
```

### 實務問題二：測試互相污染

全域 mux 只有一份，而且**沒有「移除路由」的 API**。所以測試註冊的東西清不掉，會一路累積：

```go
package main

import (
	"net/http"
	"net/http/httptest"
	"testing"
)

func TestA_我先塞了一個假路由(t *testing.T) {
	http.HandleFunc("GET /orders", func(w http.ResponseWriter, r *http.Request) {
		w.Write([]byte("假的訂單"))
	})
}

func TestB_我什麼都沒註冊(t *testing.T) {
	req := httptest.NewRequest("GET", "/orders", nil)
	if _, pattern := http.DefaultServeMux.Handler(req); pattern != "" {
		t.Errorf("被污染了：我沒註冊 /orders，卻看得到 %q", pattern)
	}
}
```

```text
--- PASS: TestA_我先塞了一個假路由
--- FAIL: TestB_我什麼都沒註冊
    被污染了：我沒註冊 /orders，卻看得到 "GET /orders"
```

`TestB` 單獨跑會過，跟 `TestA` 一起跑就掛——這種 bug 特別難查。

**還有第二個問題**：同一個 pattern 註冊兩次會 **panic**，所以你沒辦法寫「同一路由、多種設定」的表格測試。

**解法：把路由建構包成函式，每個測試拿一份新的。**

```go
// 正式程式碼
func NewRouter(svc *Service) *http.ServeMux {
	mux := http.NewServeMux()
	mux.HandleFunc("GET /users", svc.listUsers)
	return mux
}

// 測試
func TestRouter(t *testing.T) {
	cases := []struct{ name, want string }{
		{"中文版", "使用者清單"},
		{"英文版", "user list"},
		{"空清單", ""},
	}

	for _, tc := range cases {
		t.Run(tc.name, func(t *testing.T) {
			mux := NewRouter(newFakeService(tc.want)) // ← 每個子測試一份全新的

			rec := httptest.NewRecorder()
			mux.ServeHTTP(rec, httptest.NewRequest("GET", "/users", nil))

			if got := rec.Body.String(); got != tc.want {
				t.Errorf("got %q, want %q", got, tc.want)
			}
		})
	}
}
```

三個子測試 = 三個獨立物件，各自註冊各自的，跑完就被 GC 回收。它們之間沒有任何共用狀態，順序換掉結果也一樣。

!!! tip "一句話記憶"
    > 全域 = 大家共用一張桌子，你放的東西別人看得到、也收不走。
    > 自建 = 每個人自己一張桌子，用完就丟。

    「可測試性」常常不取決於你怎麼寫測試，而取決於**被測的東西能不能被建立第二份**。

## ServeMux 的路由

!!! version "Go 1.22：ServeMux 支援方法與路徑參數"
    這是標準庫路由多年來最大的一次升級。Go 1.22 之前，`http.ServeMux` 只支援前綴比對，沒有方法區分、沒有路徑參數——所以幾乎每個專案都要引入 `chi`、`gorilla/mux` 之類的第三方路由器。

    Go 1.22 起，標準庫就夠用了。

```go
package main

import (
	"fmt"
	"net/http"
)

func main() {
	mux := http.NewServeMux()

	// 方法 + 路徑參數
	mux.HandleFunc("GET /users/{id}", func(w http.ResponseWriter, r *http.Request) {
		id := r.PathValue("id")
		fmt.Fprintf(w, "取得使用者 %s", id)
	})

	mux.HandleFunc("POST /users", func(w http.ResponseWriter, r *http.Request) {
		fmt.Fprintln(w, "建立使用者")
	})

	mux.HandleFunc("DELETE /users/{id}", func(w http.ResponseWriter, r *http.Request) {
		fmt.Fprintf(w, "刪除使用者 %s", r.PathValue("id"))
	})

	// 萬用尾綴：{path...} 會匹配剩下的所有路徑段
	mux.HandleFunc("GET /files/{path...}", func(w http.ResponseWriter, r *http.Request) {
		fmt.Fprintf(w, "檔案路徑: %s", r.PathValue("path"))
	})

	// 結尾的 {$} 表示「精確匹配」，不會匹配子路徑
	mux.HandleFunc("GET /{$}", func(w http.ResponseWriter, r *http.Request) {
		fmt.Fprintln(w, "首頁")
	})

	// 主機名比對
	mux.HandleFunc("api.example.com/health", func(w http.ResponseWriter, r *http.Request) {
		fmt.Fprintln(w, "ok")
	})

	http.ListenAndServe(":8080", mux)
}
```

### 模式語法

| 模式 | 意義 |
| --- | --- |
| `/users` | 精確路徑（會匹配 `/users` 與重導 `/users/`） |
| `/users/` | 前綴，匹配 `/users/` 底下所有路徑 |
| `/users/{$}` | **只**匹配 `/users/`，不匹配子路徑 |
| `GET /users` | 限定 HTTP 方法 |
| `/users/{id}` | 單一路徑段的參數，用 `r.PathValue("id")` 取得 |
| `/files/{path...}` | 匹配剩餘的所有路徑段 |
| `example.com/x` | 限定主機名 |

### 優先順序規則

**最具體的模式勝出**，跟註冊順序無關：

```text
/users/{id}/posts   比  /users/{id}/   更具體  → 前者勝
GET /users/{id}     比  /users/{id}    更具體  → 前者勝
/users/admin        比  /users/{id}    更具體  → 前者勝
```

如果兩個模式互相衝突（誰也不比誰具體），`ServeMux` 會在註冊時 **panic**——在啟動時就發現問題，而不是執行期才出現奇怪的行為。

!!! tip "還需要第三方路由器嗎"
    Go 1.22 之後，大部分專案不需要了。仍然值得考慮第三方的情況：

    - 需要**路由群組**與**群組層級的中介層**（`chi` 的 `r.Route` / `r.Use`）
    - 需要正規表示式約束（`/users/{id:[0-9]+}`）
    - 需要極致的路由效能（`httprouter` 的 radix tree）
    - 已有大量既存程式碼

    純標準庫加上自己寫的中介層鏈，對多數服務已經綽綽有餘。

## 中介層

### 這是什麼

中介層（middleware）是一個**吃 `http.Handler`、吐 `http.Handler`** 的函式。它把原本的 handler 包起來，在前後插入自己的邏輯（記錄、認證、限流、recover）。

Go 沒有內建的中介層機制，但 `http.Handler` 介面讓它自然成立：

```go
func Middleware(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		// 請求進來時
		next.ServeHTTP(w, r)
		// 回應出去後
	})
}
```

能一層包一層，是因為 `http.HandlerFunc` 這個轉換：

```go
type HandlerFunc func(ResponseWriter, *Request)

func (f HandlerFunc) ServeHTTP(w ResponseWriter, r *Request) { f(w, r) }
```

`http.Handler` 是介面，只要有 `ServeHTTP` 方法就算數。`http.HandlerFunc(fn)` 是一次**型別轉換**，把普通函式轉成一個帶有 `ServeHTTP` 方法的型別，藉此滿足介面。

### 執行時機：包裝時 vs 服務時

這是中介層最容易誤解的地方，也是實務 bug 的主要來源。**外層函式本體只跑一次，回傳的 closure 每個請求跑一次。**

```go
package main

import (
	"fmt"
	"net/http"
	"net/http/httptest"
)

func Demo(next http.Handler) http.Handler {
	fmt.Println("[A] 外層本體 —— 包裝時，只有這一次")

	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		fmt.Println("    [B] closure —— 每個請求一次:", r.URL.Path)
		defer fmt.Println("    [D] defer —— 每個請求一次:", r.URL.Path)
		next.ServeHTTP(w, r)
	})
}

func main() {
	mux := http.NewServeMux()
	mux.HandleFunc("GET /ok", func(w http.ResponseWriter, r *http.Request) {
		fmt.Println("        [C] handler 本體")
	})

	fmt.Println("--- 啟動階段 ---")
	h := Demo(mux) // ← Demo 在這裡被呼叫，就這麼一次

	for i := 1; i <= 2; i++ {
		fmt.Printf("\n--- 請求 %d ---\n", i)
		h.ServeHTTP(httptest.NewRecorder(), httptest.NewRequest("GET", "/ok", nil))
	}
}
```

```text
--- 啟動階段 ---
[A] 外層本體 —— 包裝時，只有這一次

--- 請求 1 ---
    [B] closure —— 每個請求一次: /ok
        [C] handler 本體
    [D] defer —— 每個請求一次: /ok

--- 請求 2 ---
    [B] closure —— 每個請求一次: /ok
        [C] handler 本體
    [D] defer —— 每個請求一次: /ok
```

`[A]` 只出現一次，`[B]`／`[D]` 每個請求都出現。

原因很單純：`Demo(mux)` 是普通的函式呼叫，在 `ListenAndServe` 求值引數時就執行完了。存進 server 的是它**回傳的那個 closure**，之後每個請求由 server 的 goroutine 呼叫它的 `ServeHTTP`：

```text
ListenAndServe
  └─ 接受連線 → 每條連線一個 goroutine
       └─ 讀出請求 → handler.ServeHTTP(w, r)   ← 就是那個 closure
            ├─ [B] closure 開始，註冊 defer
            ├─ next.ServeHTTP(w, r) → mux 路由 → [C] 你的 handler
            └─ [D] defer 執行（正常回傳或 panic 都會）
```

### 實務問題：把初始化寫進 closure

知道時機之後，這個 bug 就很明顯了——但它不會報錯，只會安靜地失效：

```go
// ✗ 限流完全沒有作用
func RateLimiter(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		limiter := rate.NewLimiter(10, 30) // ← 每個請求都建一個新的！
		if !limiter.Allow() {              //    永遠 Allow，因為 burst 是滿的
			http.Error(w, "too many requests", http.StatusTooManyRequests)
			return
		}
		next.ServeHTTP(w, r)
	})
}

// ✓ 放在 return 之前 —— 全服務共用一個，只建一次
func RateLimiter(next http.Handler) http.Handler {
	limiter := rate.NewLimiter(10, 30)

	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		if !limiter.Allow() {
			http.Error(w, "too many requests", http.StatusTooManyRequests)
			return
		}
		next.ServeHTTP(w, r)
	})
}
```

同樣的規則適用於：編譯正規表示式、解析模板、建立連線池、載入設定、初始化 metrics counter。

**判準**：這個東西是「全服務共用一份」還是「每個請求一份」？前者放外層，後者放 closure。

### 實務問題：順序反直覺

```go
handler := Logging(Recoverer(Auth(mux)))
```

**包裝是由內而外**（`Auth(mux)` 先算出來），但**請求流向是由外而內**：

```text
請求 → Logging → Recoverer → Auth → mux → handler
回應 ← Logging ← Recoverer ← Auth ← mux ← handler
```

實務上的取捨：

- `Recoverer` 越外層，保護範圍越大。
- 但要放在 `Logging` **裡面**，否則 panic 的請求不會出現在存取日誌裡（`Logging` 的 `defer` 會先被 panic 跳過）。
- `Auth` 要在業務 handler 之前，但通常在 `Logging` 之後——你會想記錄到「被拒絕的請求」。

一般順序：`Logging → Recoverer → CORS → 限流 → Auth → 業務 handler`。

### 串接多個中介層

```go
package main

import (
	"log/slog"
	"net/http"
	"time"
)

type Middleware func(http.Handler) http.Handler

// 串接多個中介層：Chain(a, b, c)(h) 等於 a(b(c(h)))
func Chain(mws ...Middleware) Middleware {
	return func(next http.Handler) http.Handler {
		for i := len(mws) - 1; i >= 0; i-- {
			next = mws[i](next)
		}
		return next
	}
}

// 需要包裝 ResponseWriter 才能取得 status code
type statusWriter struct {
	http.ResponseWriter
	status int
	bytes  int
}

func (w *statusWriter) WriteHeader(code int) {
	w.status = code
	w.ResponseWriter.WriteHeader(code)
}

func (w *statusWriter) Write(b []byte) (int, error) {
	if w.status == 0 {
		w.status = http.StatusOK
	}
	n, err := w.ResponseWriter.Write(b)
	w.bytes += n
	return n, err
}

func Logging(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		start := time.Now()
		sw := &statusWriter{ResponseWriter: w}

		next.ServeHTTP(sw, r)

		slog.Info("request",
			"method", r.Method,
			"path", r.URL.Path,
			"status", sw.status,
			"bytes", sw.bytes,
			"duration", time.Since(start),
		)
	})
}

func main() {
	mux := http.NewServeMux()
	mux.HandleFunc("GET /hello", func(w http.ResponseWriter, r *http.Request) {
		w.Write([]byte("hi"))
	})

	handler := Chain(Logging)(mux)
	http.ListenAndServe(":8080", handler)
}
```

!!! danger "包裝 ResponseWriter 會弄丟可選介面"
    `http.ResponseWriter` 的實作還會滿足 `http.Flusher`、`http.Hijacker`、`io.ReaderFrom` 等介面。你的 `statusWriter` 只嵌入了 `ResponseWriter`，這些額外介面就消失了——SSE（需要 `Flush`）、WebSocket 升級（需要 `Hijack`）都會壞掉。

    **解法：用 `http.NewResponseController`（Go 1.20+）。**

    ```go
    rc := http.NewResponseController(w)
    rc.Flush()                                   // 會穿透包裝層找到真正的 Flusher
    rc.SetWriteDeadline(time.Now().Add(time.Minute))
    ```

    它會沿著 `Unwrap() http.ResponseWriter` 方法鏈往下找。所以你的包裝型別應該提供：

    ```go
    func (w *statusWriter) Unwrap() http.ResponseWriter { return w.ResponseWriter }
    ```

## 客戶端：Transport 與連線池

`http.Client` 是薄薄一層，真正做事的是 `http.Transport`——它管理連線池、TLS 握手、HTTP/2 升級。

```go
package main

import (
	"net"
	"net/http"
	"time"
)

var client = &http.Client{
	Timeout: 10 * time.Second, // 涵蓋整個請求：連線 + 送出 + 讀完 body

	Transport: &http.Transport{
		DialContext: (&net.Dialer{
			Timeout:   3 * time.Second,  // 建立 TCP 連線
			KeepAlive: 30 * time.Second, // TCP keep-alive 探測
		}).DialContext,

		TLSHandshakeTimeout:   5 * time.Second,
		ResponseHeaderTimeout: 5 * time.Second,
		ExpectContinueTimeout: 1 * time.Second,

		MaxIdleConns:        100, // 全部主機加起來的閒置連線上限
		MaxIdleConnsPerHost: 10,  // 每個主機的閒置連線上限（預設只有 2！）
		MaxConnsPerHost:     50,  // 每個主機的總連線上限（0 = 無限）
		IdleConnTimeout:     90 * time.Second,

		ForceAttemptHTTP2: true,
	},
}
```

### 兩個最常見的效能問題

**① `MaxIdleConnsPerHost` 預設只有 2**

```go
// 預設值
DefaultMaxIdleConnsPerHost = 2
```

如果你的服務高頻呼叫同一個下游 API，只有 2 條連線能被重用，其餘的每次都要重新建立（TCP 三次握手 + TLS 握手）。**這是 Go 微服務最常見的效能陷阱之一。**

呼叫同一個後端時，把它調到跟你的並行度相當：

```go
MaxIdleConnsPerHost: 100,
```

**② 每次請求都建立新的 Client 或 Transport**

```go
// ✗ 每次都新的 Transport → 連線池完全沒作用，還會累積 TIME_WAIT
func fetch(url string) {
	client := &http.Client{Transport: &http.Transport{}}
	client.Get(url)
}

// ✓ 全域共用一個
var client = &http.Client{ /* ... */ }
```

`http.Client` 與 `http.Transport` 都是**並行安全**的，設計上就是要被共用。

!!! danger "必須讀完並關閉 response body"
    ```go
    resp, err := client.Get(url)
    if err != nil {
        return err
    }
    defer resp.Body.Close()

    // 就算不需要內容，也要讀完
    io.Copy(io.Discard, resp.Body)
    ```

    **只 `Close` 而不讀完，連線不會回到池子裡**——它會被直接關掉。在高頻呼叫下，這等於連線池完全失效，而且會累積大量 TIME_WAIT 狀態的連線，可能耗盡本地埠號。

    這是 Go 客戶端程式碼最常見的 bug。

### 一定要傳 context

```go
func fetch(ctx context.Context, url string) ([]byte, error) {
	req, err := http.NewRequestWithContext(ctx, http.MethodGet, url, nil)
	if err != nil {
		return nil, err
	}

	resp, err := client.Do(req)
	if err != nil {
		return nil, err
	}
	defer resp.Body.Close()

	if resp.StatusCode != http.StatusOK {
		io.Copy(io.Discard, resp.Body) // 仍要讀完
		return nil, fmt.Errorf("非預期的狀態碼: %d", resp.StatusCode)
	}

	return io.ReadAll(io.LimitReader(resp.Body, 10<<20)) // 限制大小，防惡意的巨大回應
}
```

三個重點：`NewRequestWithContext` 讓請求可被取消、非 2xx 也要讀完 body、用 `io.LimitReader` 防止記憶體被打爆。

## 優雅關閉

```go
package main

import (
	"context"
	"errors"
	"log/slog"
	"net/http"
	"os"
	"os/signal"
	"syscall"
	"time"
)

func main() {
	mux := http.NewServeMux()
	mux.HandleFunc("GET /health", func(w http.ResponseWriter, r *http.Request) {
		w.Write([]byte("ok"))
	})

	srv := &http.Server{
		Addr:              ":8080",
		Handler:           mux,
		ReadHeaderTimeout: 5 * time.Second,
		IdleTimeout:       120 * time.Second,
	}

	// 在背景啟動
	go func() {
		if err := srv.ListenAndServe(); err != nil && !errors.Is(err, http.ErrServerClosed) {
			slog.Error("listen failed", "err", err)
			os.Exit(1)
		}
	}()
	slog.Info("伺服器啟動", "addr", srv.Addr)

	// 等待中斷訊號
	stop := make(chan os.Signal, 1)
	signal.Notify(stop, os.Interrupt, syscall.SIGTERM)
	<-stop

	slog.Info("開始優雅關閉…")

	ctx, cancel := context.WithTimeout(context.Background(), 30*time.Second)
	defer cancel()

	if err := srv.Shutdown(ctx); err != nil {
		slog.Error("強制關閉", "err", err)
		srv.Close()
	}

	slog.Info("已關閉")
}
```

`Shutdown` 做的事：

1. 停止接受新連線
2. 關閉所有閒置的 keep-alive 連線
3. 等待進行中的請求完成（或 context 逾時）

!!! warning "`Shutdown` 不會等 hijack 的連線與背景 goroutine"
    WebSocket（hijack）連線與你在 handler 裡開的背景 goroutine，`Shutdown` 都管不到。這些要自己用 `sync.WaitGroup` 或 context 追蹤。

    也記得 `signal.Notify` 的 channel **必須有緩衝**（至少 1）。無緩衝的話，訊號送達時如果沒人在接收，會被直接丟棄。

## HTTP/2 與 HTTP/3

**HTTP/2 是預設開啟的**（僅限 HTTPS）。`net/http` 會在 TLS 握手時透過 ALPN 協商，成功就自動用 HTTP/2。

```go
// 想關掉 HTTP/2
tr := &http.Transport{
	TLSNextProto: map[string]func(string, *tls.Conn) http.RoundTripper{},
}
```

觀察實際使用的版本：

```go
fmt.Println(resp.Proto) // HTTP/2.0 或 HTTP/1.1
```

**HTTP/3（QUIC）目前不在標準庫裡**，需要用 `github.com/quic-go/quic-go`。

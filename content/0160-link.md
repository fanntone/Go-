## Plan 9 組合語言

Go 的組合語言不是 Intel 語法也不是 AT&T 語法，而是繼承自 **Plan 9** 作業系統的一種**半抽象組合語言**。理解它的關鍵是：**它不是 CPU 的真實指令集，而是一層薄薄的抽象**。

### 三個要記住的差異

**① 運算元順序是「來源，目的」**

```text
MOVQ AX, BX      // Plan 9：把 AX 搬到 BX
mov  rbx, rax    // Intel 語法：把 rax 搬到 rbx（順序相反！）
```

**② 暫存器沒有前綴，而且有虛擬暫存器**

除了 `AX`、`BX`、`SP` 這些真實暫存器，Plan 9 還有四個**虛擬暫存器**：

| 虛擬暫存器 | 意義 |
| --- | --- |
| `SB` | Static Base，全域符號的基底。`foo(SB)` 表示符號 `foo` |
| `FP` | Frame Pointer，函式參數的基底。`x+0(FP)` 表示第一個參數 |
| `SP` | Stack Pointer，區域變數的基底。注意這跟硬體的 SP 不完全一樣 |
| `PC` | Program Counter |

**③ 指令後綴標示運算元大小**

`MOVB`（1 位元組）、`MOVW`（2）、`MOVL`（4）、`MOVQ`（8）。

### 讀一段實際輸出

```go
package main

type Point struct{ X, Y int }

func Dist2(p Point) int {
	return p.X*p.X + p.Y*p.Y
}

func main() {
	println(Dist2(Point{3, 4}))
}
```

```bash
go tool compile -S -l main.go
```

```text
main.Dist2 STEXT nosplit size=17 args=0x10 locals=0x0 funcid=0x0 align=0x0
	0x0000 00000 (main.go:5)	TEXT	main.Dist2(SB), NOSPLIT|ABIInternal, $0-16
	0x0000 00000 (main.go:6)	IMULQ	AX, AX
	0x0004 00004 (main.go:6)	IMULQ	BX, BX
	0x0008 00008 (main.go:6)	LEAQ	(BX)(AX*1), AX
	0x000c 00012 (main.go:6)	RET
```

逐項拆解 `TEXT` 那一行：

| 部分 | 意義 |
| --- | --- |
| `main.Dist2(SB)` | 符號名稱，`SB` 表示這是全域符號 |
| `NOSPLIT` | 不插入堆疊成長檢查（函式夠小且不呼叫別人） |
| `ABIInternal` | 使用 Go 1.17+ 的暫存器呼叫慣例 |
| `$0-16` | 區域變數 0 位元組；參數 + 回傳值共 16 位元組 |

然後看指令本身：`Point{3, 4}` 的兩個欄位被拆開放進 `AX` 與 `BX`（**struct 被打散進暫存器**，沒有經過記憶體），兩次 `IMULQ` 做平方，`LEAQ (BX)(AX*1), AX` 用位址計算指令做加法（比 `ADDQ` 少一個旗標更新，是常見的窺孔最佳化）。

整個函式沒有碰記憶體，也沒有函式序言／尾聲（prologue/epilogue）。這就是暫存器 ABI 加上內聯之後的效果。

!!! note "什麼時候你真的需要寫組合語言"
    幾乎不需要。標準庫裡有組合語言的地方主要是三類：CPU 指令的直接存取（`math/bits`、`crypto` 的 AES-NI／AVX2 實作）、runtime 的堆疊切換與 goroutine 切換、系統呼叫的入口。

    如果你在寫應用程式碼而想用組合語言優化，通常代表演算法或資料結構層面還有更大的空間沒挖。

## 暫存器配置

SSA 的最後幾個 pass 裡，`regalloc` 負責決定每個值放在哪。這是 NP-hard 問題，實務上用啟發式演算法。

`amd64` 上可用的通用暫存器有 16 個，但其中幾個被保留：

| 暫存器 | 用途 |
| --- | --- |
| `SP` (`RSP`) | 堆疊指標 |
| `BP` (`RBP`) | 影格指標（frame pointer），用於堆疊追蹤 |
| `R14` | 目前的 `g`（goroutine 結構的指標） |
| `R12` | 暫時用途，連結器可能改寫 |
| 其餘 | 可自由配置 |

`R14` 專門存 `g` 這件事很關鍵。Go 的每個 goroutine 都有一個 `g` 結構，runtime 需要「隨時能拿到目前是哪個 g」。把它固定在暫存器裡，讓 `getg()` 幾乎零成本——這對堆疊成長檢查（每個函式序言都要做）非常重要。

當值多於暫存器時，多出來的會**溢出（spill）**到堆疊。`ssa.html` 的最後幾欄可以看到 spill/restore 指令。

## 目標檔與連結

編譯完每個套件會得到一個 `.a` 檔（其實是 Go 自訂格式的封存檔）。連結器 `cmd/link` 把它們與 `runtime` 合併成一顆執行檔。

### 連結器做的四件事

**① 符號解析。** 每個 `.a` 檔裡有「我定義了哪些符號」與「我需要哪些符號」。連結器把它們對起來，填入真實位址。找不到就是 `undefined: xxx`。

**② 死碼消除。** 從進入點（`runtime.rt0_go`）開始做可達性分析，沒被引用到的函式與資料整個丟掉。這是 Go 執行檔沒有比實際更大的原因。

```go
package main

import "fmt"

func neverCalled() {
	fmt.Println("我不會出現在執行檔裡")
}

func main() {
	fmt.Println("hi")
}
```

```bash
go build -o app.exe . 
go tool nm app.exe | findstr "neverCalled"
```

沒有輸出——`neverCalled` 被刪掉了。

!!! warning "反射會擋住死碼消除"
    如果你的程式用了 `reflect.Value.Method` 或 `reflect.Type.Method`，連結器就無法確定哪些方法會被呼叫，只好**保留所有型別的所有方法**。這會讓執行檔明顯變大。

    這也是為什麼大量使用反射的框架（某些 ORM、DI 容器）產出的執行檔特別肥。

**③ 產生中繼資料。** 執行檔裡除了程式碼，還有幾塊 runtime 需要的表：

| 區段 | 內容 |
| --- | --- |
| `pclntab` | PC → 行號／函式名對應表，`panic` 印堆疊追蹤靠它 |
| `moduledata` | 模組層級的中繼資料，GC 與反射的入口 |
| `typelinks` | 所有型別的 `_type` 描述子，型別斷言與反射用 |
| `itablinks` | 已知的 (介面, 具體型別) 配對表 |
| `gcdata` / `gcbss` | 全域變數裡哪些位置是指標，GC 掃描用 |
| `funcdata` / `pcdata` | 每個函式的堆疊圖（stack map），GC 掃描堆疊用 |

**④ 產生平台的執行檔格式。** Windows 是 PE、Linux 是 ELF、macOS 是 Mach-O。

### 執行檔為什麼這麼大

一支只印 hello world 的 Go 程式，編出來大約 1.5–2 MB。原因是**靜態連結**：runtime（排程器、GC、記憶體配置器）全部包進去了，還有上面那些中繼資料表。

想瘦身：

```bash
# 去掉除錯資訊與符號表，通常能少 25–30%
go build -ldflags="-s -w" -o app.exe .
```

| 旗標 | 作用 | 代價 |
| --- | --- | --- |
| `-s` | 去掉符號表 | `go tool nm` 失效 |
| `-w` | 去掉 DWARF 除錯資訊 | delve/gdb 無法除錯 |

!!! tip "`-s -w` 不影響 panic 堆疊追蹤"
    很多人以為加了 `-s -w` 之後 panic 就印不出函式名了。**不會**。堆疊追蹤靠的是 `pclntab`，那是 runtime 必需的資料，不會被這兩個旗標移除。被移除的是 DWARF（給外部除錯器用）與符號表（給 `nm`／`objdump` 用）。

再進一步可以用 `upx` 之類的壓縮器，但那會拖慢啟動並可能觸發防毒軟體誤判，一般不建議。

### 看看誰佔了空間

```bash
go tool nm -size -sort size app.exe
```

或用社群工具 `go-size-analyzer` / `goweight` 分析各套件的貢獻。常見的肥胖來源：

- `net/http`（連帶拉進 `crypto/tls`）
- `regexp`
- 大量使用反射的第三方套件
- `time` 的時區資料庫（可用 build tag `timetzdata` 控制）

## 常用的連結器旗標

### 注入版本資訊

這是最實用的一招。用 `-X` 在建置時設定字串變數：

```go
package main

import "fmt"

var (
	version   = "dev"
	commit    = "none"
	buildTime = "unknown"
)

func main() {
	fmt.Printf("version=%s commit=%s built=%s\n", version, commit, buildTime)
}
```

```bash
go build -ldflags="-X main.version=1.2.3 -X main.commit=$(git rev-parse --short HEAD)" -o app.exe .
```

限制：只能設定 **`string` 型別的套件層變數**，而且該變數不能是常數、不能已經有非空的初始值（有初始值的話會被覆蓋，但不保證）。

!!! tip "Go 1.18 起有內建的版本資訊"
    如果你只是想知道 commit hash，不必自己注入。Go 會自動把 VCS 資訊嵌入執行檔：

    ```go
    package main

    import (
        "fmt"
        "runtime/debug"
    )

    func main() {
        info, ok := debug.ReadBuildInfo()
        if !ok {
            return
        }
        for _, s := range info.Settings {
            if s.Key == "vcs.revision" || s.Key == "vcs.time" || s.Key == "vcs.modified" {
                fmt.Printf("%s = %s\n", s.Key, s.Value)
            }
        }
    }
    ```

    也可以在命令列查：`go version -m app.exe`

### 其他常用旗標

| 旗標 | 用途 |
| --- | --- |
| `-s -w` | 縮小體積（見上） |
| `-X pkg.Var=value` | 注入字串變數 |
| `-extldflags "-static"` | 搭配 cgo 時強制完全靜態連結 |
| `-H windowsgui` | Windows 上不開主控台視窗（GUI 程式用） |
| `-buildmode=c-shared` | 產生 C 可呼叫的共享函式庫 |
| `-linkmode=external` | 用系統連結器而非 Go 內建的 |

## 交叉編譯

Go 最受歡迎的特性之一。只要不用 cgo，換兩個環境變數就能編出其他平台的執行檔：

```bash
GOOS=linux GOARCH=amd64 go build -o app-linux .
GOOS=darwin GOARCH=arm64 go build -o app-mac .
GOOS=windows GOARCH=amd64 go build -o app.exe .
```

PowerShell：

```text
$env:GOOS = "linux"; $env:GOARCH = "amd64"
go build -o app-linux .
Remove-Item Env:GOOS, Env:GOARCH
```

看看支援哪些組合：

```bash
go tool dist list
```

!!! danger "cgo 會毀掉交叉編譯"
    只要你的相依樹裡有任何一個套件用了 cgo（常見的是 `mattn/go-sqlite3`、部分影像處理套件、某些 DNS 解析路徑），交叉編譯就需要目標平台的 C 交叉編譯工具鏈，難度陡增。

    純 Go 的專案請保持 `CGO_ENABLED=0`，並在 CI 裡強制檢查：

    ```bash
    CGO_ENABLED=0 go build ./...
    ```

    這也順帶讓執行檔完全靜態連結，可以放進 `FROM scratch` 的容器映像。

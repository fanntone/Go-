5.2同步原語與鎖

Mutex 的正常模式與飢餓模式、RWMutex 的寫入者優先、WaitGroup 與 Once 的實作，以及 atomic 與記憶體模型。

對照版本 · Go 1.26

為什麼需要鎖#

Go 的口號是「用通訊來共享記憶體，而不是用共享記憶體來通訊」。但這不表示 channel 是萬用解——保護一小塊共享狀態時，mutex 通常更簡單也更快。

判斷準則：

情境 建議
保護一個 struct 的欄位 sync.Mutex
讀多寫少的共享資料 sync.RWMutex
單一計數器或旗標 sync/atomic
在 goroutine 之間傳遞資料所有權 channel
協調工作流程、pipeline channel
等待一組 goroutine 完成 sync.WaitGroup / errgroup
只執行一次的初始化 sync.Once

sync.Mutex#

結構#

type Mutex struct {
    _ noCopy
    mu isync.Mutex  // Go 1.24 起實作搬到 internal/sync
}

實際的狀態是一個 int32，位元拆成四個部分：

位元 名稱 意義
0 mutexLocked 是否已被鎖住
1 mutexWoken 有 goroutine 被喚醒中，不要再喚醒別人
2 mutexStarving 是否處於飢餓模式
3–31 waiterCount 等待中的 goroutine 數量

兩種模式#

這是 sync.Mutex 設計上最巧妙的地方。

自旋的條件#

進入等待佇列前，Lock 會嘗試「自旋」——不休眠，忙碌等待幾個 CPU 週期。這只在下列條件全部成立時發生：

  1. 自旋次數還沒超過 4 次
  2. 多核心機器（GOMAXPROCS > 1）
  3. 至少有一個其他的 P 處於執行狀態
  4. 目前 P 的本地執行佇列是空的（沒有別的工作可做）
  5. 鎖處於正常模式

理由：如果持鎖者很快就會釋放（常見情況），自旋比「休眠 + 喚醒」便宜得多。但如果沒有其他核心在跑，自旋就是純粹浪費——持鎖者根本沒機會執行。

使用注意事項#

package main

import (
    "fmt"
    "sync"
)

type Counter struct {
    mu sync.Mutex // ✓ 放在被保護欄位的正上方，慣例上表示保護範圍
    n  int
}

func (c *Counter) Inc() {
    c.mu.Lock()
    defer c.mu.Unlock()
    c.n++
}

func (c *Counter) Value() int {
    c.mu.Lock()
    defer c.mu.Unlock()
    return c.n
}

func main() {
    c := &Counter{} // ✓ 用指標，避免複製
    var wg sync.WaitGroup
    for range 1000 {
        wg.Add(1)
        go func() { defer wg.Done(); c.Inc() }()
    }
    wg.Wait()
    fmt.Println(c.Value()) // 1000
}

Mutex 絕對不能複製

// ✗ 複製了鎖的狀態
func (c Counter) Bad() { // 值接收者！
    c.mu.Lock()          // 鎖的是複本
    defer c.mu.Unlock()
}

sync.Mutex 內含 noCopy 標記，go vet 會抓到：

./main.go:12:6: Bad passes lock by value: main.Counter contains sync.Mutex

含有 mutex 的 struct，所有方法都必須用指標接收者。 這也連帶表示這種 struct 不該被當成 map 的值型別（m[k].Inc() 會取到複本）。

Mutex 不可重入（non-reentrant）

func (c *Counter) IncTwice() {
    c.mu.Lock()
    defer c.mu.Unlock()
    c.Inc() // ✗ 死結！Inc 也會嘗試 Lock
}

Go 刻意不支援可重入鎖。理由是：可重入鎖會讓「這段程式碼持有哪些鎖」變得難以推理，反而更容易寫出死結。

正確做法是把不加鎖的版本抽出來：

func (c *Counter) Inc() {
    c.mu.Lock()
    defer c.mu.Unlock()
    c.incLocked()
}

func (c *Counter) IncTwice() {
    c.mu.Lock()
    defer c.mu.Unlock()
    c.incLocked()
    c.incLocked()
}

// 慣例：Locked 後綴表示「呼叫者必須已持有鎖」
func (c *Counter) incLocked() { c.n++ }

sync.RWMutex#

允許多個讀取者同時持有，但寫入者獨佔。

package main

import (
    "fmt"
    "sync"
)

type Cache struct {
    mu sync.RWMutex
    m  map[string]string
}

func (c *Cache) Get(k string) (string, bool) {
    c.mu.RLock()         // 讀鎖：可以有很多個
    defer c.mu.RUnlock()
    v, ok := c.m[k]
    return v, ok
}

func (c *Cache) Set(k, v string) {
    c.mu.Lock()          // 寫鎖：獨佔
    defer c.mu.Unlock()
    if c.m == nil {
        c.m = map[string]string{}
    }
    c.m[k] = v
}

func main() {
    c := &Cache{}
    c.Set("a", "1")
    fmt.Println(c.Get("a"))
}

寫入者優先#

RWMutex 的關鍵設計：一旦有寫入者在等待，新的讀取者就會被阻塞。

沒有這個機制的話，持續不斷的讀取請求會讓寫入者永遠等不到機會（寫入者飢餓）。

RWMutex 的讀鎖不可重入

c.mu.RLock()
defer c.mu.RUnlock()
c.someMethodThatAlsoRLocks() // ✗ 可能死結

如果在兩次 RLock 之間有寫入者提出請求，第二次 RLock 會被擋住，而第一次的 RUnlock 又還沒執行——死結。

sync.WaitGroup#

等待一組 goroutine 完成。

package main

import (
    "fmt"
    "sync"
)

func main() {
    var wg sync.WaitGroup
    results := make([]int, 5)

    for i := range 5 {
        wg.Add(1) // ✓ 在 go 之前呼叫
        go func() {
            defer wg.Done() // ✓ 用 defer，確保 panic 也會遞減
            results[i] = i * i
        }()
    }

    wg.Wait()
    fmt.Println(results) // [0 1 4 9 16]
}

三條規則：

  1. Add 必須在 go 之前呼叫。 放在 goroutine 內部的話，Wait 可能在 Add 執行前就通過了。
  2. Done 用 defer。 否則 panic 會讓 Wait 永遠卡住。
  3. 不要複製 WaitGroup。 跟 Mutex 一樣，一定要傳指標。

Go 1.25：WaitGroup.Go

Go 1.25 加入了 wg.Go(f)，把「Add + go + defer Done」三步合成一步：

var wg sync.WaitGroup
for i := range 5 {
    wg.Go(func() {
        results[i] = i * i
    })
}
wg.Wait()

這消除了忘記 Add 或忘記 Done 的可能性，建議新程式碼優先使用。

需要收集錯誤時用 errgroup#

package main

import (
    "context"
    "fmt"
    "time"

    "golang.org/x/sync/errgroup"
)

func main() {
    g, ctx := errgroup.WithContext(context.Background())
    g.SetLimit(3) // 最多 3 個並行

    for i := range 10 {
        g.Go(func() error {
            select {
            case <-time.After(10 * time.Millisecond):
                if i == 4 {
                    return fmt.Errorf("任務 %d 失敗", i)
                }
                return nil
            case <-ctx.Done():
                return ctx.Err()
            }
        })
    }

    if err := g.Wait(); err != nil {
        fmt.Println("錯誤:", err) // 任務 4 失敗
    }
}

errgroup 的三個優勢：回傳第一個錯誤、任一失敗自動取消 context、SetLimit 控制並行度。

sync.Once#

保證某段程式碼只執行一次，而且所有呼叫者都會等到它執行完。

package main

import (
    "fmt"
    "sync"
)

var (
    once   sync.Once
    config *Config
)

type Config struct{ Value string }

func GetConfig() *Config {
    once.Do(func() {
        fmt.Println("初始化中…（只會印一次）")
        config = &Config{Value: "loaded"}
    })
    return config
}

func main() {
    var wg sync.WaitGroup
    for range 5 {
        wg.Add(1)
        go func() { defer wg.Done(); _ = GetConfig() }()
    }
    wg.Wait()
    fmt.Println(GetConfig().Value)
}

實作要點#

type Once struct {
    done atomic.Uint32
    m    Mutex
}

func (o *Once) Do(f func()) {
    if o.done.Load() == 0 {   // 快路徑：一次原子讀取
        o.doSlow(f)
    }
}

func (o *Once) doSlow(f func()) {
    o.m.Lock()
    defer o.m.Unlock()
    if o.done.Load() == 0 {   // 雙重檢查
        defer o.done.Store(1) // f 執行完才設定
        f()
    }
}

兩個細節值得注意：

  • done 在 f() 完成後才設定（用 defer）。這保證「Do 回傳時，f 一定已經跑完」——否則其他 goroutine 可能看到半初始化的狀態。
  • f panic 也算「執行過」。defer o.done.Store(1) 在 panic 展開時仍會執行，之後的 Do 不會重試。如果需要重試語意，得自己實作。

Go 1.21：OnceFunc、OnceValue、OnceValues

// 更簡潔的寫法
var getConfig = sync.OnceValue(func() *Config {
    return &Config{Value: "loaded"}
})

func main() {
    cfg := getConfig() // 第一次執行，之後回傳快取值
}

OnceValues 支援 (T, error) 的回傳形式，很適合「只初始化一次但可能失敗」的場景。

sync/atomic#

單一變數的無鎖操作。比 mutex 快一個數量級，但只能保護單一變數。

Go 1.19：型別化的原子型別

舊的函式式 API（atomic.AddInt64(&x, 1)）容易誤用——很容易忘記某處直接讀寫了 x。Go 1.19 加入型別化版本，把不安全的存取從型別系統上排除：

package main

import (
    "fmt"
    "sync"
    "sync/atomic"
)

type Stats struct {
    requests atomic.Int64
    errors   atomic.Int64
    enabled  atomic.Bool
    handler  atomic.Pointer[Handler]
}

type Handler struct{ Name string }

func main() {
    var s Stats
    s.enabled.Store(true)
    s.handler.Store(&Handler{Name: "v1"})

    var wg sync.WaitGroup
    for range 1000 {
        wg.Add(1)
        go func() {
            defer wg.Done()
            s.requests.Add(1)
        }()
    }
    wg.Wait()

    fmt.Println(s.requests.Load())      // 1000
    fmt.Println(s.enabled.Load())       // true
    fmt.Println(s.handler.Load().Name)  // v1

    // CAS：只在目前值符合預期時才更新
    old := s.requests.Load()
    ok := s.requests.CompareAndSwap(old, old+100)
    fmt.Println(ok, s.requests.Load())  // true 1100
}

可用型別：atomic.Int32、Int64、Uint32、Uint64、Uintptr、Bool、Pointer[T]、Value。

atomic.Value 的用途：無鎖設定熱更新#

package main

import (
    "fmt"
    "sync/atomic"
)

type Config struct {
    Timeout int
    Retries int
}

var cfg atomic.Pointer[Config]

func Get() *Config { return cfg.Load() }

func Reload(c *Config) { cfg.Store(c) } // 整份替換，讀取端完全無鎖

func main() {
    Reload(&Config{Timeout: 30, Retries: 3})
    fmt.Println(*Get())

    Reload(&Config{Timeout: 60, Retries: 5})
    fmt.Println(*Get())
}

讀取路徑完全沒有鎖，只有一次原子指標載入。這是高頻讀取設定的最佳模式。關鍵是 Config 本身不可變——要更新就整份替換，絕不修改既有的那份。

記憶體模型與 -race#

happens-before#

Go 的記憶體模型定義了「一個 goroutine 的寫入，什麼時候保證能被另一個 goroutine 看到」。核心是 happens-before 關係：

建立 happens-before 的操作
go 陳述式 happens-before 新 goroutine 開始執行
channel 傳送 happens-before 對應的接收完成
channel 關閉 happens-before 接收到零值
無緩衝 channel 的接收 happens-before 對應傳送完成
mu.Unlock() happens-before 之後的 mu.Lock() 回傳
once.Do(f) 中 f 的完成 happens-before 任何 Do 回傳
原子操作依照 sequential consistency 排序

沒有 happens-before 關係的並行讀寫就是資料競爭（data race），行為未定義。

package main

// ✗ 典型的資料競爭
var done bool
var msg string

func setup() {
    msg = "hello"
    done = true // 沒有同步 → 另一個 goroutine 可能先看到 done=true 而 msg=""
}

func main() {
    go setup()
    for !done { // 忙碌等待，而且可能永遠看不到 done 變 true
    }
    println(msg)
}

編譯器可能把 for !done {} 最佳化成 if !done { for {} }（因為它看不到任何會改變 done 的同步操作），程式就永遠卡住。

正確寫法用 channel 或 atomic：

var done = make(chan struct{})
var msg string

func setup() {
    msg = "hello"
    close(done) // 建立 happens-before
}

func main() {
    go setup()
    <-done
    println(msg) // 保證看到 "hello"
}

一定要跑 -race#

go test -race ./...
go run -race main.go
go build -race -o app-race .

競爭偵測器會報告：

WARNING: DATA RACE
Write at 0x00c000112010 by goroutine 7:
  main.setup()
      /tmp/main.go:9 +0x2e

Previous read at 0x00c000112010 by main goroutine:
  main.main()
      /tmp/main.go:14 +0x3c

-race 的成本與限制

  • 記憶體用量增加 5–10 倍，速度慢 2–20 倍。 不要在正式環境長期開啟。
  • 只能偵測「實際發生」的競爭。 沒被觸發的程式碼路徑不會被檢查——所以測試覆蓋率很重要。
  • CI 一定要跑。 這是最划算的投資：資料競爭造成的 bug 極難重現，也極難除錯。

建議做法：CI 上跑 go test -race ./...，正式環境用一般建置。

常見錯誤與解法#

同步原語的 bug 有個共通特徵：大多不會立刻出錯，而是在特定的時序下偶發。所以「本機測試都過」完全不能當作沒問題的證據——-race 才是。

症狀 原因 解法
計數對不上、資料偶爾錯亂 複製了含 mutex 的 struct 全部方法用指標接收者
程式偶發卡死 錯誤路徑漏了 Unlock defer mu.Unlock()
讀多的場景卻死結 RLock 巢狀呼叫 抽出不加鎖的內部版本
WaitGroup 永遠不返回 Add 寫在 goroutine 內、或漏了 Done Add 在 go 之前、defer wg.Done()
初始化失敗後不再重試 Once 內 panic 也算執行過 自己實作重試，或用 OnceValues
用了 atomic 還是有競爭 複合操作不是原子的 CompareAndSwap 或改用鎖
高並行下吞吐上不去 鎖競爭 mutex profile 找熱點、分片

① 複製了含 mutex 的 struct#

package main

import "sync"

type Counter struct {
    mu sync.Mutex
    n  int
}

// ✗ 值接收者：每次呼叫都複製一份，鎖的是複本
// （go vet 會抓到這個錯誤：passes lock by value）
func (c Counter) IncBad() {
    c.mu.Lock()
    defer c.mu.Unlock()
    c.n++ // 改的也是複本
}

// ✓ 指標接收者
func (c *Counter) Inc() {
    c.mu.Lock()
    defer c.mu.Unlock()
    c.n++
}

func main() {
    c := &Counter{}
    c.Inc()
}

go vet ./...

./main.go:11:6: IncBad passes lock by value: main.Counter contains sync.Mutex

go vet 抓得到這一種，一定要放進 CI。 它同時涵蓋 sync.Mutex、RWMutex、WaitGroup、Once、Cond——這些型別內部都有 noCopy 標記。

同樣的道理：含 mutex 的 struct 不該當 map 的值型別，因為 m[k] 取出來的是複本：

// ✗ m[k].Inc() 根本不能編譯（不可定址），改成這樣也是錯的
m := map[string]Counter{}
c := m["a"]
c.Inc()      // 改的是複本
m["a"] = c   // 這中間有競爭窗口

// ✓ 存指標
m := map[string]*Counter{}
m["a"].Inc()

② 錯誤路徑漏了 Unlock#

// ✗ 中間 return 就再也解不開了
func (c *Cache) Get(k string) (string, error) {
    c.mu.Lock()

    v, ok := c.m[k]
    if !ok {
        return "", ErrNotFound // ← 鎖沒放！之後所有人都卡住
    }

    c.mu.Unlock()
    return v, nil
}

// ✓
func (c *Cache) Get(k string) (string, error) {
    c.mu.Lock()
    defer c.mu.Unlock()

    v, ok := c.m[k]
    if !ok {
        return "", ErrNotFound
    }
    return v, nil
}

這個 bug 的症狀是整個服務在某個時間點突然全部卡死，而且堆疊追蹤裡一堆 goroutine 停在 sync.(*Mutex).Lock。

診斷方式：

curl "http://localhost:6060/debug/pprof/goroutine?debug=2" | grep -A5 "sync.(\*Mutex).Lock"

預設就用 defer。只有在確定「函式後半段跟共享狀態無關」時，才手動 Unlock 縮小臨界區。

③ RWMutex 的讀鎖不可重入#

// ✗ 可能死結
func (c *Cache) Get(k string) string {
    c.mu.RLock()
    defer c.mu.RUnlock()

    return c.format(k) // format 內部也 RLock → 危險
}

func (c *Cache) format(k string) string {
    c.mu.RLock()       // ← 如果這中間有寫入者在等，這裡會卡住
    defer c.mu.RUnlock()
    return c.m[k]
}

為什麼會死結：RWMutex 是寫入者優先的。一旦有寫入者提出請求，後續的 RLock 就會被擋住——但第一層的 RUnlock 還沒執行，寫入者也拿不到鎖。三方互相等待。

解法是慣例做法：把不加鎖的版本抽出來，用 Locked 後綴標示「呼叫者必須已持有鎖」。

func (c *Cache) Get(k string) string {
    c.mu.RLock()
    defer c.mu.RUnlock()
    return c.formatLocked(k)
}

// formatLocked 假設呼叫者已持有鎖
func (c *Cache) formatLocked(k string) string {
    return c.m[k]
}

Mutex 也一樣不可重入，理由與寫法都相同（見使用注意事項）。

④ WaitGroup 的兩個經典誤用#

// ✗ Add 寫在 goroutine 裡
for i := 0; i < 3; i++ {
    go func() {
        wg.Add(1)      // ← Wait 可能在這之前就通過了
        defer wg.Done()
        work()
    }()
}
wg.Wait() // 可能立刻返回，什麼都沒等到

// ✗ 沒用 defer，panic 時計數不會遞減
go func() {
    work()      // 這裡 panic 的話…
    wg.Done()   // …永遠執行不到 → Wait 永遠卡住
}()

正確寫法：

for i := 0; i < 3; i++ {
    wg.Add(1)              // ✓ 在 go 之前
    go func() {
        defer wg.Done()    // ✓ 用 defer
        work()
    }()
}
wg.Wait()

Go 1.25：wg.Go 讓這兩個錯誤不可能發生

for i := 0; i < 3; i++ {
    wg.Go(func() { work() })
}
wg.Wait()

Add、go、defer Done 三步合成一步。新程式碼優先用這個。

⑤ sync.Once 裡 panic 之後不會重試#

package main

import (
    "fmt"
    "sync"
)

var (
    once sync.Once
    conn string
)

func connect(fail bool) {
    once.Do(func() {
        if fail {
            panic("連線失敗")
        }
        conn = "connected"
    })
}

func main() {
    func() {
        defer func() { fmt.Println("第一次:", recover()) }()
        connect(true)
    }()

    connect(false) // 不會再執行了
    fmt.Printf("conn = %q\n", conn)
}

第一次: 連線失敗
conn = ""

Once 內部用 defer o.done.Store(1) 標記完成，panic 展開時那個 defer 仍會執行。所以「失敗了下次重試」的語意不成立——初始化失敗之後，後續所有呼叫都會安靜地拿到半成品。

需要重試語意就別用 Once：

type lazyConn struct {
    mu   sync.Mutex
    conn *Conn
}

func (l *lazyConn) Get() (*Conn, error) {
    l.mu.Lock()
    defer l.mu.Unlock()

    if l.conn != nil {
        return l.conn, nil
    }
    c, err := dial()
    if err != nil {
        return nil, err // ✓ 失敗不記錄狀態，下次會再試
    }
    l.conn = c
    return c, nil
}

⑥ atomic 的複合操作不是原子的#

// ✗ Load 與 Store 之間有窗口，兩個 goroutine 可能同時進來
if counter.Load() < limit {
    counter.Add(1)
}

// ✓ 用 CompareAndSwap 迴圈
for {
    cur := counter.Load()
    if cur >= limit {
        break
    }
    if counter.CompareAndSwap(cur, cur+1) {
        break
    }
    // CAS 失敗表示有人搶先改了，重讀再試
}

atomic 保證的是「單一操作」的原子性，不是你寫的那段邏輯。只要涉及「先讀、判斷、再寫」，就需要 CAS 或直接用鎖。

一個實用的判準：如果你的原子操作超過一行，八成該用 mutex。 可讀性的損失通常不值得那點效能。

⑦ 找出鎖競爭的熱點#

高並行下吞吐上不去，但 CPU 沒滿——通常是鎖競爭。

package main

import (
    "net/http"
    _ "net/http/pprof"
    "runtime"
)

func init() {
    runtime.SetMutexProfileFraction(5) // 取樣 1/5 的競爭事件
    runtime.SetBlockProfileRate(10000) // 每 10 微秒的阻塞取樣一次
}

func main() {
    mux := http.NewServeMux()
    // … 手動註冊 pprof，見 net/http 那章
    _ = mux
}

go tool pprof -http=:8081 http://localhost:6060/debug/pprof/mutex
go tool pprof -http=:8081 http://localhost:6060/debug/pprof/block
  • mutex profile —— 哪把鎖被爭用最久
  • block profile —— goroutine 阻塞在哪（含 channel）

兩個剖析都有效能成本

SetMutexProfileFraction 與 SetBlockProfileRate 都會拖慢程式。只在診斷期間開啟，不要長期留在正式環境。取樣率也不要設 1（全採樣）。

找到熱點之後的處理順序：縮小臨界區 → 換成 RWMutex（讀多時）→ 分片 → 改用無鎖結構。前兩項通常就夠了。

效能對照#

操作 大致成本（無競爭）
atomic.Int64.Add ~5 ns
atomic.Int64.Load ~0.3 ns
Mutex.Lock + Unlock ~15 ns
RWMutex.RLock + RUnlock ~20 ns
RWMutex.Lock + Unlock ~25 ns
無緩衝 channel 收發 ~150 ns
有緩衝 channel 收發（未滿） ~50 ns

有競爭時，數字會急遽惡化——mutex 在高競爭下可能到微秒級，因為涉及 goroutine 休眠與喚醒。

這張表最重要的訊息：channel 比 mutex 貴一個數量級。用 channel 傳遞資料所有權、協調流程是對的；用 channel 當互斥鎖（ch := make(chan struct{}, 1)）就是繞遠路。

1.4中間表示與 SSA

walk 階段如何把語法糖改寫成 runtime 呼叫、SSA 是什麼、以及編譯器在 SSA 上做了哪些最佳化。

對照版本 · Go 1.26

walk：語法糖的終點#

型別檢查完成後，編譯器把 AST 轉成內部 IR（cmd/compile/internal/ir），接著進入 walk 階段。這個階段做的事情，用一句話講就是：把語言特性改寫成普通的函式呼叫與運算。

這一步至關重要，因為它解釋了 Go 大半的「魔法」。

你寫的 walk 之後大致變成
s = append(s, x) 容量檢查 + runtime.growslice（不夠時）+ 寫入
v, ok := m[k] runtime.mapaccess2(typ, m, &k)
m[k] = v runtime.mapassign(typ, m, &k)
delete(m, k) runtime.mapdelete(typ, m, &k)
for k, v := range m runtime.mapIterInit + mapIterNext 迴圈
for i, v := range s 傳統的 for i := 0; i < len(s); i++
ch <- v runtime.chansend1(ch, &v)
v := <-ch runtime.chanrecv1(ch, &v)
select { ... } runtime.selectgo(...)
go f(x) runtime.newproc(fn, args)
defer f(x) 開放編碼／runtime.deferprocStack／deferproc
panic(v) runtime.gopanic(v)
x.(T) runtime.assertE2T 系列或內聯的型別比較
make([]int, n) runtime.makeslice(typ, n, n)
new(T) / 逃逸的 T{} runtime.newobject(typ)
copy(dst, src) runtime.memmove 或 runtime.slicecopy
s1 + s2（字串） runtime.concatstring2
[]byte(s) runtime.stringtoslicebyte

親眼看到改寫

-W 印出 walk 之前的 IR，-w 印出之後的。對照兩者最有教育意義：

go tool compile -w main.go

你會直接看到 append 消失、runtime.growslice 出現。

這張表值得記住。之後每一章討論某個特性的成本時，起點都是「它被改寫成哪個 runtime 呼叫」。Go 沒有魔法，只有你看不見的函式呼叫。

什麼是 SSA#

walk 之後，IR 被轉成 SSA（Static Single Assignment，靜態單賦值） 形式。這是現代編譯器後端的通用中間表示，LLVM、V8、HotSpot 都用它。

SSA 只有一條核心規則：每個變數只被賦值一次。

看一段普通程式碼：

x := 1
x = x + 2
x = x * 3
y := x + 1

轉成 SSA 後，每次賦值都變成一個新變數：

x₁ = 1
x₂ = x₁ + 2
x₃ = x₂ * 3
y₁ = x₃ + 1

為什麼這個限制有用#

因為它讓「這個值從哪來」變成一眼可見的事實。

在原本的形式裡，要知道 y := x + 1 裡的 x 是哪個值，編譯器得往回掃描找最後一次賦值，而且遇到分支就要考慮所有可能路徑。在 SSA 裡，x₃ 就是 x₃，定義只有一個地方。這叫 def-use 鏈明確化，幾乎所有資料流最佳化都因此變簡單。

分支怎麼辦：φ 函式#

問題來了。如果值來自不同分支呢？

var x int
if cond {
    x = 1
} else {
    x = 2
}
use(x)

use(x) 裡的 x 可能是 x₁ 也可能是 x₂。SSA 用一個虛構的 φ（phi）函式表示「依控制流選擇」：

b1: if cond → b2 else b3
b2: x₁ = 1;  goto b4
b3: x₂ = 2;  goto b4
b4: x₃ = φ(x₁, x₂)
    use(x₃)

φ 函式不對應任何真實指令。它只是編譯器的記帳方式，在最後產生機器碼時會被拆解成暫存器搬移或直接靠暫存器配置消解掉。

SSA 上的最佳化#

Go 編譯器在 SSA 形式上跑數十個 pass，每個 pass 做一件小事，串起來效果顯著。以下挑幾個最有感的。

常數傳播與摺疊#

func f() int {
    a := 3
    b := 4
    return a*a + b*b
}

整個函式會被摺成 return 25。連乘法都不會執行。

死碼消除（DCE）#

func g(x int) int {
    y := expensive() // 若 y 沒被用到，且 expensive 沒有副作用 → 整個呼叫被刪
    _ = y
    return x * 2
}

注意「沒有副作用」這個前提。編譯器要能證明呼叫是純函式才敢刪，否則保留。

邊界檢查消除（BCE）#

Go 對每次 slice 索引都會插入邊界檢查，這是記憶體安全的基礎。但很多檢查在編譯期就能證明是多餘的，prove 這個 pass 負責找出來。

package main

func sum(s []int) int {
    total := 0
    for i := 0; i < len(s); i++ {
        total += s[i] // i < len(s) 已經被迴圈條件保證 → 檢查被消除
    }
    return total
}

驗證方式：

go build -gcflags="-d=ssa/check_bce/debug=1" ./main.go

沒有輸出就代表所有檢查都被消除了。有輸出的話會標出哪一行還留著檢查。

幫助編譯器消除檢查的技巧 —— 在迴圈前加一行看似多餘的斷言：

func scale(dst, src []float64) {
    if len(dst) < len(src) {
        panic("dst too short")
    }
    _ = dst[len(src)-1] // 提示：dst 至少有 len(src) 個元素
    for i, v := range src {
        dst[i] = v * 2 // dst[i] 的檢查可以被消除
    }
}

去虛擬化（devirtualization）#

介面方法呼叫需要透過 itab 間接跳轉，無法內聯。如果編譯器能證明介面裡裝的一定是某個具體型別，就可以改成直接呼叫：

var w io.Writer = os.Stdout // 編譯器知道具體型別
w.Write(b)                  // 可以去虛擬化成 (*os.File).Write

PGO 引導的去虛擬化：Go 1.21 起

大部分情況下編譯器無法靜態證明介面裡是什麼。Go 1.21 起，如果你提供剖析檔（profile），編譯器可以看到「這個呼叫點 95% 的時候都是 *os.File」，於是產生：

if 具體型別 == *os.File {
    直接呼叫（可內聯）
} else {
    走原本的介面分派
}

這叫推測式去虛擬化。Go 1.24 起這個最佳化也支援介面方法以外的間接函式呼叫。

其他重要的 pass#

Pass 做什麼
opt 一般化的窺孔最佳化（peephole），依架構規則改寫指令
cse 公共子運算式消除：同樣的計算只做一次
nilcheckelim 消除多餘的 nil 檢查
loopbce 迴圈相關的邊界檢查消除
writebarrier 插入 GC 寫入屏障（見 垃圾回收器）
lower 把架構無關的 SSA op 降階成具體 CPU 指令
regalloc 暫存器配置，決定哪些值放暫存器、哪些溢出到堆疊
stackalloc 為溢出的值配置堆疊空間

用 GOSSAFUNC 看整個過程#

這是本節最值得動手做的實驗。

package main

func clamp(x, lo, hi int) int {
    if x < lo {
        return lo
    }
    if x > hi {
        return hi
    }
    return x
}

func main() {
    println(clamp(15, 0, 10))
}

PowerShell：

$env:GOSSAFUNC = "clamp"
go build -o nul .\main.go
Remove-Item Env:GOSSAFUNC

Bash：

GOSSAFUNC=clamp go build -o /dev/null ./main.go

打開產生的 ssa.html，你會看到：

  1. 最左邊是 start —— 剛從 IR 轉過來的 SSA，指令又多又囉嗦，充滿 Load 與 Store。
  2. 中間幾十欄是各個 pass。注意觀察 opt、prove、deadcode 之後指令數的變化。
  3. 最右邊是 genssa —— 最終的機器指令。

滑鼠移到任一個值上，所有 pass 裡對應的值都會高亮。這讓你可以追蹤「這個常數是在哪個 pass 被摺掉的」。

為什麼 Go 只有幾十個 pass，LLVM 有數百個

這是刻意的取捨。Go 團隊給編譯器設的目標是「編譯速度不能退步」，新的最佳化如果讓編譯變慢太多就不會被接受。

結果是 Go 的產出比 clang -O2 慢一些，但編譯速度快一個數量級。對「改一行、跑一次測試」這個開發迴圈來說，後者的價值往往更高。

SSA 之後#

暫存器配置完成後，SSA 值被指派到實體暫存器或堆疊位置，φ 函式被消解，最後由 cmd/internal/obj 產生目標平台的機器碼與目標檔。

不過在進入後端之前，中端還有兩個對你的程式碼影響最大的最佳化沒談：內聯與逃逸分析。它們決定了你的函式呼叫要不要付出代價、你的變數要配置在堆疊還是堆積。這是下一節的主題。

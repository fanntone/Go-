7.5程式碼生成

go:generate 的運作方式、用 go/ast 與 text/template 寫產生器，以及什麼時候該用它取代反射。

對照版本 · Go 1.26

為什麼需要程式碼生成#

Go 刻意不提供巨集（macro）與樣板元編程。當你需要「依型別產生重複的程式碼」時，有三個選項：

方案 成本 型別安全 適合
反射 執行期慢 100 倍 執行期才發現錯誤 型別在編譯期未知
泛型 幾乎零成本 編譯期檢查 演算法與容器
程式碼生成 零執行期成本 編譯期檢查 需要走訪 struct 欄位、產生樣板

泛型解決了很多以前需要生成的場景（通用容器、Map／Filter），但它不能走訪 struct 的欄位——這正是序列化、ORM、驗證器需要的能力。這些場景仍然是「反射 vs 生成」的選擇。

go:generate 的機制#

//go:generate stringer -type=Status

規則很簡單：

  1. 必須是註解，而且 // 後面沒有空格（// go:generate 不會被辨識）。
  2. 必須在行首（可以有前導空白，但不能在其他程式碼後面）。
  3. go generate ./... 會掃描所有 .go 檔，依序執行這些指令。

go build 不會執行 go:generate

這是刻意的設計：生成的程式碼要提交進版控。

理由是： - 建置不需要額外工具鏈，go build 永遠能跑 - 程式碼審查時看得到生成結果的變化 - CI 不需要安裝一堆產生器

做法是在 CI 加一步檢查「生成結果有沒有過期」：

go generate ./...
git diff --exit-code   # 有差異就代表忘了重新生成

可用的變數#

go generate 會設定幾個環境變數：

變數 內容
$GOFILE 目前檔案名稱
$GOLINE 這行指令的行號
$GOPACKAGE 套件名稱
$GOARCH / $GOOS 目標架構與作業系統
$DOLLAR 一個 $ 字元（用於需要跳脫時） 
//go:generate echo "處理 $GOFILE（套件 $GOPACKAGE）"

最常用的產生器：stringer#

為 iota 常數產生 String() 方法。

package main

import "fmt"

//go:generate go run golang.org/x/tools/cmd/stringer@latest -type=Status -linecomment

type Status int

const (
    StatusPending Status = iota // 待處理
    StatusRunning               // 執行中
    StatusDone                  // 已完成
    StatusFailed                // 失敗
)

func main() {
    fmt.Println(StatusRunning)          // 執行中
    fmt.Printf("%v %d\n", StatusDone, StatusDone) // 已完成 2
}

go generate ./...

會產生 status_string.go：

// Code generated by "stringer -type=Status -linecomment"; DO NOT EDIT.

package main

import "strconv"

func _() {
    // 編譯期斷言：如果常數值改變，這裡會編譯失敗
    var x [1]struct{}
    _ = x[StatusPending-0]
    _ = x[StatusRunning-1]
    _ = x[StatusDone-2]
    _ = x[StatusFailed-3]
}

const _Status_name = "待處理執行中已完成失敗"

var _Status_index = [...]uint8{0, 9, 18, 27, 33}

func (i Status) String() string {
    if i < 0 || i >= Status(len(_Status_index)-1) {
        return "Status(" + strconv.FormatInt(int64(i), 10) + ")"
    }
    return _Status_name[_Status_index[i]:_Status_index[i+1]]
}

三個值得學習的技巧：

  1. // Code generated ... DO NOT EDIT. —— 這是 Go 的正式慣例（規範在 go generate 的文件裡）。工具鏈與 linter 會辨識這一行並跳過檢查。
  2. 編譯期斷言 —— 那個 _() 函式確保常數值沒有被改動。改了就編譯失敗，而不是產生錯誤的字串。
  3. 單一字串 + 索引表 —— 比 map[Status]string 快，而且沒有初始化成本、沒有堆積配置。

用 go run pkg@version 而不是要求先安裝

//go:generate go run golang.org/x/tools/cmd/stringer@latest -type=Status

這樣任何人 clone 下來就能 go generate，不需要先 go install 一堆工具。版本也可以釘死（把 @latest 換成 @v0.24.0），保證所有人產生的結果一致。

或者用 tool 指令（Go 1.24+）管理工具相依：

go get -tool golang.org/x/tools/cmd/stringer

會記錄在 go.mod 的 tool 區塊，之後 go tool stringer 就能執行。

常用的產生器#

工具 用途
stringer 為 iota 常數產生 String()
mockgen（go.uber.org/mock） 從介面產生測試用的 mock
sqlc 從 SQL 產生型別安全的查詢函式

自己寫產生器#

以「為 struct 產生 setter 方法」為例，完整示範一次。

第一步：解析原始碼#

用 golang.org/x/tools/go/packages 載入套件（它比 go/parser 好，因為會一併載入型別資訊）：

//go:build ignore

package main

import (
    "bytes"
    "fmt"
    "go/ast"
    "go/format"
    "go/token"
    "log"
    "os"
    "strings"
    "text/template"

    "golang.org/x/tools/go/packages"
)

type Field struct {
    Name string
    Type string
}

type Target struct {
    Name   string
    Fields []Field
}

func main() {
    if len(os.Args) < 3 {
        log.Fatal("用法: gen <套件路徑> <型別名稱>")
    }
    pkgPath, typeName := os.Args[1], os.Args[2]

    cfg := &packages.Config{
        Mode: packages.NeedName | packages.NeedSyntax | packages.NeedTypes | packages.NeedTypesInfo,
    }
    pkgs, err := packages.Load(cfg, pkgPath)
    if err != nil {
        log.Fatal(err)
    }
    if len(pkgs) == 0 || len(pkgs[0].Errors) > 0 {
        log.Fatalf("載入失敗: %v", pkgs[0].Errors)
    }
    pkg := pkgs[0]

    target := findStruct(pkg, typeName)
    if target == nil {
        log.Fatalf("找不到 struct %q", typeName)
    }

    out, err := render(pkg.Name, target)
    if err != nil {
        log.Fatal(err)
    }

    fname := strings.ToLower(typeName) + "_setters.go"
    if err := os.WriteFile(fname, out, 0o644); err != nil {
        log.Fatal(err)
    }
    fmt.Println("已產生", fname)
}

func findStruct(pkg *packages.Package, name string) *Target {
    var found *Target

    for _, file := range pkg.Syntax {
        ast.Inspect(file, func(n ast.Node) bool {
            ts, ok := n.(*ast.TypeSpec)
            if !ok || ts.Name.Name != name {
                return true
            }
            st, ok := ts.Type.(*ast.StructType)
            if !ok {
                return true
            }

            t := &Target{Name: name}
            for _, f := range st.Fields.List {
                for _, id := range f.Names {
                    if !id.IsExported() {
                        continue
                    }
                    t.Fields = append(t.Fields, Field{
                        Name: id.Name,
                        Type: exprString(f.Type),
                    })
                }
            }
            found = t
            return false
        })
    }
    return found
}

func exprString(e ast.Expr) string {
    var buf bytes.Buffer
    format.Node(&buf, token.NewFileSet(), e)
    return buf.String()
}

const tpl = `// Code generated by gen; DO NOT EDIT.

package {{.Package}}

{{range .Fields -}}
// Set{{.Name}} 設定 {{.Name}} 並回傳接收者，支援串接。
func (x *{{$.Type}}) Set{{.Name}}(v {{.Type}}) *{{$.Type}} {
    x.{{.Name}} = v
    return x
}

{{end -}}
`

func render(pkgName string, t *Target) ([]byte, error) {
    tmpl := template.Must(template.New("setters").Parse(tpl))

    var buf bytes.Buffer
    data := struct {
        Package string
        Type    string
        Fields  []Field
    }{pkgName, t.Name, t.Fields}

    if err := tmpl.Execute(&buf, data); err != nil {
        return nil, err
    }

    // ✓ 一定要跑 format.Source，這樣模板的縮排就不用寫得很完美
    return format.Source(buf.Bytes())
}

第二步：在目標檔案加上指令#

package model

//go:generate go run ./cmd/gen . User

type User struct {
    ID    int64
    Name  string
    Email string
    tags  []string // 未匯出，會被跳過
}

第三步：執行#

go generate ./...

產生 user_setters.go：

// Code generated by gen; DO NOT EDIT.

package model

// SetID 設定 ID 並回傳接收者，支援串接。
func (x *User) SetID(v int64) *User {
    x.ID = v
    return x
}

// SetName 設定 Name 並回傳接收者，支援串接。
func (x *User) SetName(v string) *User {
    x.Name = v
    return x
}

// SetEmail 設定 Email 並回傳接收者，支援串接。
func (x *User) SetEmail(v string) *User {
    x.Email = v
    return x
}

寫產生器的五個原則#

  1. 一定要輸出 // Code generated ... DO NOT EDIT.，而且必須是第一行（在 package 之前）。格式規範在 go generate 文件。
  2. 一定要跑 format.Source()。 這樣你的模板不需要處理縮排，而且輸出保證符合 gofmt。
  3. 產生器本身加上 //go:build ignore，避免它被當成套件的一部分編譯。
  4. 失敗要 os.Exit(1)。 go generate 遇到非零退出碼會停止並回報。
  5. 輸出要有決定性（deterministic）。 走訪 map 時記得排序 key，否則每次產生的結果順序不同，diff 會很亂。

embed：另一種「生成」#

Go 1.16 的 embed 讓你把檔案直接編進執行檔，很多場景可以取代程式碼生成。

package main

import (
    "embed"
    "fmt"
    "html/template"
    "io/fs"
    "net/http"
    "os"
)

//go:embed static/*
var staticFS embed.FS

//go:embed templates/*.html
var tmplFS embed.FS

//go:embed version.txt
var version string // 單一檔案可以直接嵌成 string

//go:embed config.json
var configData []byte // 或 []byte

func main() {
    // 嵌入的檔案系統可以直接當 http.FileSystem 用
    sub, _ := fs.Sub(staticFS, "static")
    http.Handle("GET /static/", http.StripPrefix("/static/", http.FileServer(http.FS(sub))))

    tmpl := template.Must(template.ParseFS(tmplFS, "templates/*.html"))
    _ = tmpl

    fmt.Fprintln(os.Stdout, "版本:", version)
    fmt.Fprintln(os.Stdout, "設定大小:", len(configData))
}

規則與限制#

規則 說明
必須 import "embed" 就算只用 string／[]byte 也要（可用 _ "embed"）
只能嵌入同目錄或子目錄的檔案 不能用 ../
預設不含 . 與 _ 開頭的檔案 用 all: 前綴才會包含（//go:embed all:static）
不能嵌入符號連結
變數必須在套件層級 不能是區域變數
會增加執行檔大小 嵌入 100 MB 就多 100 MB

embed 通常比程式碼生成好

以前要把靜態檔案打包進執行檔，得用 go-bindata 這類工具把檔案轉成一個巨大的 Go 原始碼檔。embed 是原生支援，不需要生成步驟、不會弄髒版控、編譯也更快。

只要是「把檔案內容帶進執行檔」的需求，優先用 embed。

決策樹#

面對「重複的樣板程式碼」時，按這個順序評估：

需要處理的東西在編譯期已知嗎？
├─ 否 → 反射（沒有別的選擇）
└─ 是
   ├─ 只是要把檔案內容帶進來？
   │  → embed
   │
   ├─ 是通用的演算法或容器（不需要看 struct 欄位）？
   │  → 泛型
   │
   ├─ 需要走訪 struct 欄位／產生方法／從外部規格產生程式碼？
   │  → 程式碼生成
   │
   └─ 重複的程式碼不多（< 3 處）？
      → 直接手寫。生成有它自己的維護成本

不要為了消除三行重複而引入產生器。 程式碼生成的成本包括：多一個建置步驟、CI 要檢查是否過期、新人要理解那些「不要編輯」的檔案從哪來、產生器本身也是要維護的程式碼。

它在下面這些情況才划算：

  • 重複出現在數十個型別上（序列化、mock）
  • 來源是外部規格（.proto、OpenAPI、SQL schema）—— 這時生成是唯一能保證同步的方式
  • 反射的成本已經量測出來是瓶頸

全書結語#

從一份 .go 檔案出發，我們走過了：

  • 編譯器如何把它變成機器碼，以及逃逸分析與內聯這兩個決定效能的關鍵最佳化
  • 資料結構在記憶體裡的真實樣貌——三欄位的 slice、Swiss Table 的 map、不可變的 string
  • 語言核心的實作：暫存器呼叫慣例、介面的 itab 分派、反射建立在型別描述子之上
  • 關鍵字其實大多是編譯器改寫成的 runtime 呼叫
  • 並行：GMP 排程器、channel 的直接交遞、netpoller 讓阻塞變便宜
  • 記憶體：三層配置器、三色標記 GC、會自己長大的堆疊
  • 標準庫幾個重要套件的設計取捨

貫穿全書的一條線是：Go 沒有魔法，只有你看不見的函式呼叫。

append 是 growslice，go f() 是 newproc，m[k] 是 mapaccess。當你知道每個語法糖背後對應到哪個 runtime 函式，效能問題就從「玄學」變成「可以量測與推理的東西」。

三個帶得走的習慣：

  1. 量測，不要猜。 -gcflags=-m、-benchmem、pprof、trace —— 工具箱 那節的六件工具，遇到問題時逐一過一遍。
  2. 先減少配置，再調參數。 allocs/op 降下來，ns/op 與 GC 壓力通常會跟著降。調 GOGC 只是把問題往後推。
  3. 看原始碼。 $(go env GOROOT)/src/runtime/ 就在你的機器上。本書引用的每個函式，你都可以自己翻開來看。

祝閱讀愉快。

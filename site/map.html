2.3雜湊表 map

Go 1.24 把 map 從 bucket 鏈結換成 Swiss Table。控制字元組、可延伸雜湊、為什麼走訪順序是隨機的、以及為什麼不能取 map 元素的位址。

對照版本 · Go 1.26

一次重大的重寫#

Go 1.24 是 map 實作史上最大的一次改變。舊版用的是「bucket + 溢位鏈結」，新版換成 Swiss Table（源自 Google 的 Abseil 函式庫）加上可延伸雜湊（extendible hashing）。

官方回報的效果：查找快 30% 上下，插入與刪除也有明顯改善，而且記憶體佔用通常更低。

版本對照

版本 實作 原始碼位置
≤ 1.23 bucket（每桶 8 槽）+ 溢位桶鏈結 runtime/map.go
≥ 1.24 Swiss Table + 可延伸雜湊 internal/runtime/maps/

如果你讀到的中文資料在講 hmap、bmap、tophash、「溢位桶」，那是 Go 1.23 以前的架構。本節講的是現行版本。

行為（語意）完全沒變：一樣不保證順序、一樣不能取位址、一樣不是並行安全的。變的只是內部結構與效能特性。

Swiss Table 的核心想法#

傳統開放定址雜湊表的問題是：查找時要一格一格比對鍵，每次比對都可能是一次快取未命中（cache miss），因為鍵可能很大（例如字串要追指標）。

Swiss Table 的解法是先用一小段中繼資料快速排除。

群組（group）與控制字組（control word）#

資料被組織成群組，每個群組有 8 個槽（slot），外加一個 8 位元組的控制字組。控制字組的每個位元組對應一個槽：

這個設計的價值在快取行為。舊版 map 每次探測都要碰鍵本身；Swiss Table 大部分時候只碰 8 位元組的控制字組。

探測順序#

當群組滿了，Swiss Table 不用「溢位桶鏈結」，而是繼續探測下一個群組（二次探測，quadratic probing）。當探測到第一個有空槽的群組時就可以停——因為插入時也是照同樣順序走，如果鍵存在，一定在這之前就找到了。

這消除了舊版的溢位桶：不用額外配置、不用追指標、記憶體更緊湊。

可延伸雜湊：Go 的額外需求#

原始的 Swiss Table 擴容時要一次搬完所有元素。這對 Go 不可接受，因為：

  1. Go 的 map 可能非常大，一次搬完會造成明顯的延遲毛刺。
  2. Go 需要 GC 能精確掃描 map 裡的指標。

Go 的解法是可延伸雜湊：把一個大 map 拆成多個獨立的小 Swiss Table，每個負責雜湊空間的一段。加上一層目錄（directory）做索引。

走訪順序是隨機的#

這是刻意設計的，不是實作缺陷。

package main

import "fmt"

func main() {
    m := map[string]int{"a": 1, "b": 2, "c": 3, "d": 4, "e": 5}

    for i := 0; i < 3; i++ {
        for k := range m {
            fmt.Print(k, " ")
        }
        fmt.Println()
    }
}

c d e a b 
b c d e a 
e a b c d

每次 range 開始時，runtime 會隨機選一個起始群組與起始槽。

為什麼要故意隨機

因為 Go 團隊發現，如果順序碰巧穩定，開發者就會（無意識地）依賴它，然後在某次擴容改變順序時整個炸掉。與其讓 bug 潛伏，不如讓它每次都不一樣，逼你一開始就處理。

這跟 map 的擴容機制本來就會改變順序有關——隨機化只是把「偶爾不同」變成「總是不同」。

需要固定順序時，明確排序：

package main

import (
    "fmt"
    "maps"
    "slices"
)

func main() {
    m := map[string]int{"banana": 2, "apple": 1, "cherry": 3}

    // Go 1.23+：maps.Keys 回傳迭代器，slices.Sorted 收集並排序
    for _, k := range slices.Sorted(maps.Keys(m)) {
        fmt.Println(k, m[k])
    }
}

apple 1
banana 2
cherry 3

Go 1.21 / 1.23：maps 套件

Go 1.21 加入 maps 套件（Clone、Copy、DeleteFunc、Equal）。Go 1.23 加入迭代器版本的 maps.Keys、maps.Values、maps.All，它們回傳 iter.Seq，可以直接餵給 slices.Sorted、slices.Collect。

不能取 map 元素的位址#

package main

type Point struct{ X, Y int }

func main() {
    m := map[string]Point{"a": {1, 2}}

    // ✗ 編譯錯誤：cannot take address of m["a"]
    // p := &m["a"]

    // ✗ 編譯錯誤：cannot assign to struct field m["a"].X in map
    // m["a"].X = 10

    // 只能整個取出來讀
    _ = m["a"]
}

原因：map 的元素會被搬動。 擴容或分裂時，元素會被移到新的記憶體位置。如果允許你持有一個指向元素的指標，搬動之後那個指標就指向舊位置了。

三種解法：

package main

import "fmt"

type Point struct{ X, Y int }

func main() {
    // 解法一：存指標（元素本身在堆積上，不隨 map 搬動）
    m1 := map[string]*Point{"a": {1, 2}}
    m1["a"].X = 10
    fmt.Println(*m1["a"]) // {10 2}

    // 解法二：取出、修改、寫回
    m2 := map[string]Point{"a": {1, 2}}
    p := m2["a"]
    p.X = 10
    m2["a"] = p
    fmt.Println(m2["a"]) // {10 2}

    // 解法三：用 slice 存資料，map 只存索引
    data := []Point{{1, 2}}
    idx := map[string]int{"a": 0}
    data[idx["a"]].X = 10
    fmt.Println(data[0]) // {10 2}
}

解法一最直觀但每個元素多一次配置；解法三對大量資料最有效率（連續記憶體、快取友善）。

map 不是並行安全的#

同時讀寫會直接讓程式當掉：

package main

func main() {
    m := map[int]int{}

    go func() {
        for i := 0; ; i++ {
            m[i] = i
        }
    }()
    for {
        _ = m[1]
    }
}

fatal error: concurrent map read and map write

注意這是 fatal error 不是 panic，recover() 攔不住，程式直接死。這是刻意的：並行存取 map 會破壞內部結構，繼續執行會導致記憶體毀損。

Go 在 map 的內部狀態裡放了一個旗標，寫入時設定、結束時清除。如果另一個 goroutine 在旗標設定期間進來，就觸發這個 fatal error。這不是完整的偵測（是盡力而為的檢查），所以有些競爭條件不會被抓到——用 -race 才可靠：

go run -race main.go

三種解法#

package main

import (
    "fmt"
    "sync"
)

// ① 一般用途：RWMutex 包起來
type SafeMap struct {
    mu sync.RWMutex
    m  map[string]int
}

func NewSafeMap() *SafeMap { return &SafeMap{m: make(map[string]int)} }

func (s *SafeMap) Get(k string) (int, bool) {
    s.mu.RLock()
    defer s.mu.RUnlock()
    v, ok := s.m[k]
    return v, ok
}

func (s *SafeMap) Set(k string, v int) {
    s.mu.Lock()
    defer s.mu.Unlock()
    s.m[k] = v
}

func main() {
    sm := NewSafeMap()
    var wg sync.WaitGroup
    for i := 0; i < 100; i++ {
        wg.Add(1)
        go func(n int) {
            defer wg.Done()
            sm.Set(fmt.Sprint(n), n)
        }(i)
    }
    wg.Wait()
    fmt.Println(sm.Get("42"))
}

② sync.Map —— 只在兩種特定情境下比 mutex 快： - 鍵一旦寫入就幾乎只讀（快取場景） - 多個 goroutine 各自操作不相交的鍵集合

其他情況（尤其是頻繁寫入同一批鍵）sync.Map 通常比 RWMutex 慢，因為它內部有 read/dirty 兩份結構要同步。不要因為名字有 sync 就無腦選它。

③ 分片（sharding） —— 高並行寫入時最有效：

package main

import (
    "hash/maphash"
    "sync"
)

const shards = 32

type ShardedMap struct {
    seed  maphash.Seed
    parts [shards]struct {
        mu sync.RWMutex
        m  map[string]int
    }
}

func NewSharded() *ShardedMap {
    s := &ShardedMap{seed: maphash.MakeSeed()}
    for i := range s.parts {
        s.parts[i].m = make(map[string]int)
    }
    return s
}

func (s *ShardedMap) idx(k string) int {
    return int(maphash.String(s.seed, k) % shards)
}

func (s *ShardedMap) Set(k string, v int) {
    p := &s.parts[s.idx(k)]
    p.mu.Lock()
    p.m[k] = v
    p.mu.Unlock()
}

func (s *ShardedMap) Get(k string) (int, bool) {
    p := &s.parts[s.idx(k)]
    p.mu.RLock()
    v, ok := p.m[k]
    p.mu.RUnlock()
    return v, ok
}

把鎖競爭分散到 32 把鎖上，吞吐量通常能提升好幾倍。

實用技巧#

用 map[T]struct{} 當集合#

set := map[string]struct{}{}
set["a"] = struct{}{}

if _, ok := set["a"]; ok {
    // 存在
}

struct{} 大小是 0，不佔任何空間。用 map[string]bool 每個元素會多 1 位元組（加上對齊可能更多）。

預先配置容量#

m := make(map[string]int, 10000) // 避免多次分裂與搬移

跟 slice 一樣，知道大概的元素數量就先給。

刪除不會縮小 map#

m := make(map[int]int)
for i := 0; i < 1_000_000; i++ {
    m[i] = i
}
for i := 0; i < 1_000_000; i++ {
    delete(m, i)
}
// map 現在是空的，但底層記憶體仍然是一百萬個元素的規模

Go 的 map 永遠不會縮小。要真的釋放記憶體，只能建一個新的：

m = make(map[int]int) // 舊的整個交給 GC

或用 clear(m)（Go 1.21+）—— 但注意 clear 只是清空內容，不釋放底層記憶體。

鍵型別的效能差異#

鍵型別 相對成本
int / int64 / 指標 最快，雜湊函式極簡單
string 中等，要走過整個字串算雜湊
小型陣列 / struct 中等，memhash
含介面欄位的 struct 最慢，要走執行期的型別分派

熱路徑上如果鍵是長字串，考慮先算出一個 uint64 指紋當鍵。

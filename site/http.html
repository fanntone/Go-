Go 底層原理筆記/標準函式庫與進階主題

7.2net/http

伺服器的每連線一 goroutine 模型、ServeMux 的路由（含 1.22 的新語法）、Transport 的連線池，以及必設的逾時。

對照版本 · Go 1.26

伺服器：每連線一個 goroutine#

net/http 的伺服器模型非常簡單直白：

ListenAndServe():
    ln := net.Listen("tcp", addr)
    for {
        conn := ln.Accept()
        go serve(conn)      ← 每條連線開一個 goroutine
    }

serve(conn):
    for {                   ← keep-alive：同一條連線可處理多個請求
        req := readRequest(conn)
        handler.ServeHTTP(w, req)
        if 不能 keep-alive { break }
    }
    conn.Close()

在其他語言裡，「每連線一執行緒」是眾所周知的反模式（C10K 問題）。在 Go 裡它可行，因為：

  1. goroutine 便宜 —— 2 KB 起跳，不是 8 MB。
  2. netpoller 讓阻塞的讀寫不佔用執行緒 —— 見 網路輪詢器。

結果是：你可以用最直覺的同步寫法，得到事件驅動架構的效能。

但這不代表沒有上限

每條連線至少消耗： - 一個 goroutine（2 KB 起，實際常到 8–16 KB） - 讀寫緩衝區（bufio.Reader 4 KB + bufio.Writer 4 KB） - http.Request 與相關結構

實務上每條閒置連線約 10–30 KB。 十萬條連線就是 1–3 GB。高連線數的服務仍然需要限流：

import "golang.org/x/net/netutil"

ln, _ := net.Listen("tcp", ":8080")
ln = netutil.LimitListener(ln, 10000) // 超過就不 accept
srv.Serve(ln)

逾時：唯一最重要的設定#

預設的 http.Server 沒有任何逾時。 這是 Go 標準庫少數會讓人踩雷的預設值。

package main

import (
    "net/http"
    "time"
)

func main() {
    mux := http.NewServeMux()

    srv := &http.Server{
        Addr:    ":8080",
        Handler: mux,

        // 讀取請求標頭的最長時間 —— 防 Slowloris 攻擊
        ReadHeaderTimeout: 5 * time.Second,

        // 讀完整個請求（含 body）的最長時間
        ReadTimeout: 30 * time.Second,

        // 從讀完標頭到寫完回應的最長時間
        WriteTimeout: 30 * time.Second,

        // keep-alive 連線的閒置上限
        IdleTimeout: 120 * time.Second,

        // 標頭大小上限（預設 1 MB）
        MaxHeaderBytes: 1 << 20,
    }

    srv.ListenAndServe()
}

WriteTimeout 與長時間的 handler

WriteTimeout 包含 handler 的執行時間。如果你有需要跑 5 分鐘的 handler（大檔案下載、SSE、長輪詢），設 30 秒的 WriteTimeout 會讓它被截斷。

對這類 endpoint 的解法：

// 方法一：整個伺服器不設 WriteTimeout，改在每個 handler 用 context 控制
srv := &http.Server{
    ReadHeaderTimeout: 5 * time.Second,
    // 不設 WriteTimeout
}

func normalHandler(w http.ResponseWriter, r *http.Request) {
    ctx, cancel := context.WithTimeout(r.Context(), 30*time.Second)
    defer cancel()
    doWork(ctx)
}

// 方法二：用 http.TimeoutHandler 包裝需要限制的路由
mux.Handle("/api/", http.TimeoutHandler(apiHandler, 30*time.Second, "timeout"))

ServeMux 的路由#

Go 1.22：ServeMux 支援方法與路徑參數

這是標準庫路由多年來最大的一次升級。Go 1.22 之前，http.ServeMux 只支援前綴比對，沒有方法區分、沒有路徑參數——所以幾乎每個專案都要引入 chi、gorilla/mux 之類的第三方路由器。

Go 1.22 起，標準庫就夠用了。

package main

import (
    "fmt"
    "net/http"
)

func main() {
    mux := http.NewServeMux()

    // 方法 + 路徑參數
    mux.HandleFunc("GET /users/{id}", func(w http.ResponseWriter, r *http.Request) {
        id := r.PathValue("id")
        fmt.Fprintf(w, "取得使用者 %s", id)
    })

    mux.HandleFunc("POST /users", func(w http.ResponseWriter, r *http.Request) {
        fmt.Fprintln(w, "建立使用者")
    })

    mux.HandleFunc("DELETE /users/{id}", func(w http.ResponseWriter, r *http.Request) {
        fmt.Fprintf(w, "刪除使用者 %s", r.PathValue("id"))
    })

    // 萬用尾綴：{path...} 會匹配剩下的所有路徑段
    mux.HandleFunc("GET /files/{path...}", func(w http.ResponseWriter, r *http.Request) {
        fmt.Fprintf(w, "檔案路徑: %s", r.PathValue("path"))
    })

    // 結尾的 {$} 表示「精確匹配」，不會匹配子路徑
    mux.HandleFunc("GET /{$}", func(w http.ResponseWriter, r *http.Request) {
        fmt.Fprintln(w, "首頁")
    })

    // 主機名比對
    mux.HandleFunc("api.example.com/health", func(w http.ResponseWriter, r *http.Request) {
        fmt.Fprintln(w, "ok")
    })

    http.ListenAndServe(":8080", mux)
}

模式語法#

模式 意義
/users 精確路徑（會匹配 /users 與重導 /users/）
/users/ 前綴，匹配 /users/ 底下所有路徑
/users/{$} 只匹配 /users/，不匹配子路徑
GET /users 限定 HTTP 方法
/users/{id} 單一路徑段的參數，用 r.PathValue("id") 取得
/files/{path...} 匹配剩餘的所有路徑段
example.com/x 限定主機名

優先順序規則#

最具體的模式勝出，跟註冊順序無關：

/users/{id}/posts   比  /users/{id}/   更具體  → 前者勝
GET /users/{id}     比  /users/{id}    更具體  → 前者勝
/users/admin        比  /users/{id}    更具體  → 前者勝

如果兩個模式互相衝突（誰也不比誰具體），ServeMux 會在註冊時 panic——在啟動時就發現問題，而不是執行期才出現奇怪的行為。

還需要第三方路由器嗎

Go 1.22 之後，大部分專案不需要了。仍然值得考慮第三方的情況：

  • 需要路由群組與群組層級的中介層（chi 的 r.Route / r.Use）
  • 需要正規表示式約束（/users/{id:[0-9]+}）
  • 需要極致的路由效能（httprouter 的 radix tree）
  • 已有大量既存程式碼

純標準庫加上自己寫的中介層鏈，對多數服務已經綽綽有餘。

中介層#

Go 沒有內建的中介層機制，但 http.Handler 介面讓它變得非常自然：

package main

import (
    "log/slog"
    "net/http"
    "time"
)

type Middleware func(http.Handler) http.Handler

// 串接多個中介層：Chain(a, b, c)(h) 等於 a(b(c(h)))
func Chain(mws ...Middleware) Middleware {
    return func(next http.Handler) http.Handler {
        for i := len(mws) - 1; i >= 0; i-- {
            next = mws[i](next)
        }
        return next
    }
}

// 需要包裝 ResponseWriter 才能取得 status code
type statusWriter struct {
    http.ResponseWriter
    status int
    bytes  int
}

func (w *statusWriter) WriteHeader(code int) {
    w.status = code
    w.ResponseWriter.WriteHeader(code)
}

func (w *statusWriter) Write(b []byte) (int, error) {
    if w.status == 0 {
        w.status = http.StatusOK
    }
    n, err := w.ResponseWriter.Write(b)
    w.bytes += n
    return n, err
}

func Logging(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        start := time.Now()
        sw := &statusWriter{ResponseWriter: w}

        next.ServeHTTP(sw, r)

        slog.Info("request",
            "method", r.Method,
            "path", r.URL.Path,
            "status", sw.status,
            "bytes", sw.bytes,
            "duration", time.Since(start),
        )
    })
}

func main() {
    mux := http.NewServeMux()
    mux.HandleFunc("GET /hello", func(w http.ResponseWriter, r *http.Request) {
        w.Write([]byte("hi"))
    })

    handler := Chain(Logging)(mux)
    http.ListenAndServe(":8080", handler)
}

包裝 ResponseWriter 會弄丟可選介面

http.ResponseWriter 的實作還會滿足 http.Flusher、http.Hijacker、io.ReaderFrom 等介面。你的 statusWriter 只嵌入了 ResponseWriter，這些額外介面就消失了——SSE（需要 Flush）、WebSocket 升級（需要 Hijack）都會壞掉。

解法：用 http.NewResponseController（Go 1.20+）。

rc := http.NewResponseController(w)
rc.Flush()                                   // 會穿透包裝層找到真正的 Flusher
rc.SetWriteDeadline(time.Now().Add(time.Minute))

它會沿著 Unwrap() http.ResponseWriter 方法鏈往下找。所以你的包裝型別應該提供：

func (w *statusWriter) Unwrap() http.ResponseWriter { return w.ResponseWriter }

客戶端：Transport 與連線池#

http.Client 是薄薄一層，真正做事的是 http.Transport——它管理連線池、TLS 握手、HTTP/2 升級。

package main

import (
    "net"
    "net/http"
    "time"
)

var client = &http.Client{
    Timeout: 10 * time.Second, // 涵蓋整個請求：連線 + 送出 + 讀完 body

    Transport: &http.Transport{
        DialContext: (&net.Dialer{
            Timeout:   3 * time.Second,  // 建立 TCP 連線
            KeepAlive: 30 * time.Second, // TCP keep-alive 探測
        }).DialContext,

        TLSHandshakeTimeout:   5 * time.Second,
        ResponseHeaderTimeout: 5 * time.Second,
        ExpectContinueTimeout: 1 * time.Second,

        MaxIdleConns:        100, // 全部主機加起來的閒置連線上限
        MaxIdleConnsPerHost: 10,  // 每個主機的閒置連線上限（預設只有 2！）
        MaxConnsPerHost:     50,  // 每個主機的總連線上限（0 = 無限）
        IdleConnTimeout:     90 * time.Second,

        ForceAttemptHTTP2: true,
    },
}

兩個最常見的效能問題#

① MaxIdleConnsPerHost 預設只有 2

// 預設值
DefaultMaxIdleConnsPerHost = 2

如果你的服務高頻呼叫同一個下游 API，只有 2 條連線能被重用，其餘的每次都要重新建立（TCP 三次握手 + TLS 握手）。這是 Go 微服務最常見的效能陷阱之一。

呼叫同一個後端時，把它調到跟你的並行度相當：

MaxIdleConnsPerHost: 100,

② 每次請求都建立新的 Client 或 Transport

// ✗ 每次都新的 Transport → 連線池完全沒作用，還會累積 TIME_WAIT
func fetch(url string) {
    client := &http.Client{Transport: &http.Transport{}}
    client.Get(url)
}

// ✓ 全域共用一個
var client = &http.Client{ /* ... */ }

http.Client 與 http.Transport 都是並行安全的，設計上就是要被共用。

必須讀完並關閉 response body

resp, err := client.Get(url)
if err != nil {
    return err
}
defer resp.Body.Close()

// 就算不需要內容，也要讀完
io.Copy(io.Discard, resp.Body)

只 Close 而不讀完，連線不會回到池子裡——它會被直接關掉。在高頻呼叫下，這等於連線池完全失效，而且會累積大量 TIME_WAIT 狀態的連線，可能耗盡本地埠號。

這是 Go 客戶端程式碼最常見的 bug。

一定要傳 context#

func fetch(ctx context.Context, url string) ([]byte, error) {
    req, err := http.NewRequestWithContext(ctx, http.MethodGet, url, nil)
    if err != nil {
        return nil, err
    }

    resp, err := client.Do(req)
    if err != nil {
        return nil, err
    }
    defer resp.Body.Close()

    if resp.StatusCode != http.StatusOK {
        io.Copy(io.Discard, resp.Body) // 仍要讀完
        return nil, fmt.Errorf("非預期的狀態碼: %d", resp.StatusCode)
    }

    return io.ReadAll(io.LimitReader(resp.Body, 10<<20)) // 限制大小，防惡意的巨大回應
}

三個重點：NewRequestWithContext 讓請求可被取消、非 2xx 也要讀完 body、用 io.LimitReader 防止記憶體被打爆。

優雅關閉#

package main

import (
    "context"
    "errors"
    "log/slog"
    "net/http"
    "os"
    "os/signal"
    "syscall"
    "time"
)

func main() {
    mux := http.NewServeMux()
    mux.HandleFunc("GET /health", func(w http.ResponseWriter, r *http.Request) {
        w.Write([]byte("ok"))
    })

    srv := &http.Server{
        Addr:              ":8080",
        Handler:           mux,
        ReadHeaderTimeout: 5 * time.Second,
        IdleTimeout:       120 * time.Second,
    }

    // 在背景啟動
    go func() {
        if err := srv.ListenAndServe(); err != nil && !errors.Is(err, http.ErrServerClosed) {
            slog.Error("listen failed", "err", err)
            os.Exit(1)
        }
    }()
    slog.Info("伺服器啟動", "addr", srv.Addr)

    // 等待中斷訊號
    stop := make(chan os.Signal, 1)
    signal.Notify(stop, os.Interrupt, syscall.SIGTERM)
    <-stop

    slog.Info("開始優雅關閉…")

    ctx, cancel := context.WithTimeout(context.Background(), 30*time.Second)
    defer cancel()

    if err := srv.Shutdown(ctx); err != nil {
        slog.Error("強制關閉", "err", err)
        srv.Close()
    }

    slog.Info("已關閉")
}

Shutdown 做的事：

  1. 停止接受新連線
  2. 關閉所有閒置的 keep-alive 連線
  3. 等待進行中的請求完成（或 context 逾時）

Shutdown 不會等 hijack 的連線與背景 goroutine

WebSocket（hijack）連線與你在 handler 裡開的背景 goroutine，Shutdown 都管不到。這些要自己用 sync.WaitGroup 或 context 追蹤。

也記得 signal.Notify 的 channel 必須有緩衝（至少 1）。無緩衝的話，訊號送達時如果沒人在接收，會被直接丟棄。

HTTP/2 與 HTTP/3#

HTTP/2 是預設開啟的（僅限 HTTPS）。net/http 會在 TLS 握手時透過 ALPN 協商，成功就自動用 HTTP/2。

// 想關掉 HTTP/2
tr := &http.Transport{
    TLSNextProto: map[string]func(string, *tls.Conn) http.RoundTripper{},
}

觀察實際使用的版本：

fmt.Println(resp.Proto) // HTTP/2.0 或 HTTP/1.1

HTTP/3（QUIC）目前不在標準庫裡，需要用 github.com/quic-go/quic-go。

檢查清單#

上線前對照這張表：

項目 為什麼
✓ ReadHeaderTimeout 有設 防 Slowloris
✓ IdleTimeout 有設 回收閒置連線
✓ 有 recover 中介層 一個 panic 不該弄垮整個服務
✓ 客戶端共用 http.Client 連線池才有效
✓ MaxIdleConnsPerHost 有調大 預設 2 太小
✓ response body 一律讀完並 Close 連線才能重用
✓ 請求都帶 context 可取消、可逾時
✓ 讀取 body 有大小限制 http.MaxBytesReader 或 io.LimitReader
✓ 有優雅關閉 部署時不中斷進行中的請求
✓ pprof 只綁 localhost 不要暴露內部狀態

Go 底層原理筆記/記憶體管理

6.2垃圾回收器

三色標記與寫入屏障、GC 的四個階段、GOGC 與 GOMEMLIMIT 怎麼調，以及 Go 1.26 預設啟用的 Green Tea GC。

對照版本 · Go 1.26

Go 的 GC 是什麼類型#

一句話描述：並行、三色標記清除、非分代、非壓縮、精確。

逐項拆解：

特性 意義 取捨
並行（concurrent） 標記階段與使用者程式同時執行 STW 極短（通常 < 1 ms），但需要寫入屏障
三色標記清除 mark-sweep 演算法的變體 成熟可靠，實作相對簡單
非分代 不區分新生代／老年代 少了分代假設的收益，但也省下 write barrier 的分代簿記
非壓縮 不搬移物件 指標永遠有效，cgo 與 unsafe 好處理；代價是可能有碎片
精確（precise） 明確知道每個字組是不是指標 不會誤保留垃圾；靠編譯器產生的型別中繼資料

為什麼不做分代 GC

「多數物件很快就死」的分代假設在很多語言成立。Go 團隊的判斷是：

  1. Go 的逃逸分析已經把大量短命物件留在堆疊上，這些物件根本不進 GC 的視野。分代 GC 的主要收益已經被吃掉了。
  2. 分代需要更複雜的寫入屏障（記錄跨代指標），會拖慢使用者程式碼。
  3. Go 的設計目標是低延遲而非高吞吐。分代主要優化吞吐。

這個決定曾被討論多次，目前的結論仍是不做。

三色標記#

演算法的核心是把所有物件分成三類：

顏色 意義
⚪ 白色 尚未被掃描到。標記結束時仍是白色的 = 垃圾
⚫ 灰色 已知存活，但它指向的物件還沒檢查完
⚫ 黑色 已知存活，而且它指向的物件都已經加入灰色集合

流程：

1. 全部物件初始為白色
2. 把「根物件」（全域變數、各 goroutine 的堆疊、暫存器）塗成灰色
3. while 灰色集合不為空:
       取出一個灰色物件 x
       把 x 指向的所有白色物件塗成灰色
       把 x 塗成黑色
4. 剩下的白色物件全部回收

寫入屏障#

並行標記的根本挑戰：使用者程式碼在標記期間會修改指標。

考慮這個序列：

1. GC 掃描完物件 A（塗黑），A.next = nil
2. 使用者程式碼執行：A.next = B（B 是白色）
3. 使用者程式碼執行：C.ref = nil（C 原本是唯一指向 B 的灰色物件）
4. GC 掃描結束 → B 仍是白色 → 被回收
5. 但 A.next 還指著 B → 存取已釋放的記憶體 → 災難

寫入屏障（write barrier） 是編譯器插在每個指標寫入前的一小段程式碼，用來攔截這種情況。

Go 從 1.8 起使用混合寫入屏障（hybrid write barrier），結合了兩種經典策略：

writePointer(slot, ptr):
    shade(*slot)      // Yuasa 式：把「被覆蓋掉的舊值」塗灰
    if 目前在標記階段 && 目前 goroutine 的堆疊是黑色:
        shade(ptr)    // Dijkstra 式：把「新寫入的值」也塗灰
    *slot = ptr
  • shade(*slot) 保護「即將失去參照的物件」——如果 B 原本被 A 指著，現在要被覆蓋，先把 B 塗灰保住它。
  • shade(ptr) 保護「新建立的參照」。

Go 1.8：混合屏障消除了堆疊的重新掃描

Go 1.8 之前用純 Dijkstra 屏障，但堆疊上的寫入沒有屏障（每次寫區域變數都插屏障太慢）。代價是標記結束時必須 STW 重新掃描所有 goroutine 的堆疊，這個 STW 可能長達 10–100 毫秒。

混合屏障讓堆疊在第一次掃描後就能永久標記為黑色，不需要重新掃描。STW 時間從數十毫秒降到數百微秒——這是 Go GC 延遲史上最大的一次改善。

寫入屏障的成本：標記階段的每次指標寫入都多幾道指令。這是「並行 GC」的固定稅。非標記階段時屏障會被關閉（透過一個全域旗標），成本接近零。

這解釋了一個效能現象

如果你的資料結構有大量指標且頻繁修改（例如一棵常變動的樹），GC 期間的效能會明顯下降。

對策：改用索引取代指標。用 []Node 加 int32 索引取代 *Node，寫入屏障完全消失，GC 掃描也快得多（一整塊 []Node 如果不含指標，GC 直接跳過）。

四個階段#

協助標記（mutator assist）#

如果使用者程式碼配置得比 GC 標記得還快，堆積會在 GC 完成前就超過目標。解法是：讓配置者自己幫忙標記。

每次配置時：
    assistBytes -= 配置的大小
    if assistBytes < 0:
        這個 goroutine 必須先幫忙標記一些物件，才能繼續配置

這是為什麼在 GC 期間，配置密集的程式碼會明顯變慢。 你的 goroutine 被徵召去做 GC 的工作了。

如果你在 trace 裡看到大量的 GC (assist) 事件，代表配置速率超過了 GC 的處理能力——降低配置量或提高 GOGC。

GOGC 與 GOMEMLIMIT#

GOGC：以百分比控制#

下次 GC 的目標堆積 = 上次 GC 後的存活量 × (1 + GOGC/100)

預設 GOGC=100，意思是「堆積成長到存活量的兩倍時觸發 GC」。

設定 行為 適合
GOGC=50 存活量的 1.5 倍就 GC 記憶體吃緊，願意用 CPU 換
GOGC=100 預設，2 倍 大多數情況
GOGC=400 5 倍才 GC CPU 密集、記憶體充裕
GOGC=off 完全關閉 短命的批次工具（跑完就結束） 
GOGC=200 go run main.go

或在程式裡：

import "runtime/debug"

debug.SetGCPercent(200)

GOMEMLIMIT：軟性記憶體上限#

Go 1.19 起：解決容器 OOM 的正解

GOGC 是相對的，它不知道你的容器只有 512 MB。如果存活量因為某次流量尖峰漲到 300 MB，GC 目標就變成 600 MB —— 超過容器限制，直接被 OOM Killer 殺掉。

GOMEMLIMIT 設定一個軟性上限：接近它時，GC 會更積極地運作（即使還沒到 GOGC 的門檻）。

GOMEMLIMIT=400MiB go run main.go

import "runtime/debug"

debug.SetMemoryLimit(400 << 20) // 400 MiB

它是「軟性」的： Go 會盡力不超過，但如果存活物件本身就超過限制，它不會殺掉你的程式——只會持續地跑 GC（可能陷入 GC 死亡螺旋，CPU 被 GC 吃光）。

推薦的容器設定#

容器記憶體 limit:  512 MiB
GOMEMLIMIT:        450MiB      ← 留約 10-15% 給非堆積用量
GOGC:              100 或 off

為什麼要留 10–15%？因為 GOMEMLIMIT 涵蓋的是 Go runtime 管理的記憶體總量（堆積 + 堆疊 + runtime 內部結構），但不包含：

  • cgo 配置的記憶體
  • 執行檔本身與作業系統的映射
  • 檔案系統快取

GOGC=off + GOMEMLIMIT 的組合

這個組合在某些服務上效果很好：

GOGC=off GOMEMLIMIT=450MiB ./app

意思是「不要因為堆積成長而 GC，只在接近記憶體上限時才 GC」。這讓 GC 次數降到最低（省 CPU），同時保證不會 OOM。

適合：記憶體用量穩定可預測的服務。 不適合：存活集大小變化劇烈的服務——可能長時間維持在高記憶體水位。

Green Tea GC#

Go 1.25 實驗，Go 1.26 預設啟用

這是近年 GC 最大的一次改動。

問題：傳統的標記過程把堆積當成一張扁平的指標圖，一次追一個指標。這對現代 CPU 非常不友善——每次追指標都可能是一次快取未命中，而且無法預取、無法平行化。掃描小物件時，記憶體延遲而非計算是瓶頸。

Green Tea 的做法：改變掃描的組織方式，讓 CPU 一次處理記憶體上相鄰的一批物件，而不是照指標圖的順序跳來跳去。相關資料被一起載入快取，快取命中率大幅提高，也更容易利用 CPU 的平行能力。

效果：官方回報在大量使用 GC 的真實程式上，GC 開銷降低 10%–40%。

對你的影響：升級到 Go 1.26 就自動生效，不需要改任何程式碼。想關掉（不建議）：

GOEXPERIMENT=nogreenteagc go build .

這個 opt-out 預計在 Go 1.27 移除。

其他 Go 1.26 的記憶體相關改進：

  • cgo 呼叫的基礎開銷降低約 30%
  • 64 位元平台上，runtime 會在啟動時隨機化堆積基底位址（安全強化，讓 cgo 場景下的位址預測更困難）
  • 編譯器能在更多情況下把 slice 的底層陣列配置在堆疊上

讀 gctrace#

GODEBUG=gctrace=1 go run main.go

gc 12 @2.345s 3%: 0.021+15+0.008 ms clock, 0.17+2.1/29/0.42+0.068 ms cpu, 82->84->41 MB, 84 MB goal, 0 MB stacks, 0 MB globals, 8 P

完整拆解：

片段 意義 該注意什麼
gc 12 第 12 次 GC 頻率太高 = 配置太多或 GOGC 太低
@2.345s 程式啟動後的時間
3% 至今 GC 佔用的 CPU 總比例 超過 10% 就該調校
0.021+15+0.008 ms clock STW① + 並行標記 + STW③ 兩端的 STW 是延遲關鍵，應 < 1 ms
0.17+2.1/29/0.42+0.068 ms cpu 各階段的 CPU 時間（含所有核心） 中間三段是 assist / background / idle
82->84->41 MB GC 開始 → 結束 → 存活 第三個數字是真正的「存活集大小」
84 MB goal 這次 GC 的目標
0 MB stacks goroutine 堆疊總量 大量 goroutine 時會很可觀
8 P 使用的 P 數量

三個健康指標：

  1. STW 時間 —— 第一與第三段應該都 < 1 ms。持續超過代表堆疊很多或有異常。
  2. GC CPU 比例 —— 應該 < 10%。超過表示配置速率太高。
  3. 存活集（第三個數字） —— 持續成長 = 記憶體洩漏。

調校流程#

遇到 GC 相關的效能問題，按這個順序處理：

第一步：先量測#

GODEBUG=gctrace=1 ./app 2>gc.log

確認問題類型：

症狀 可能原因
GC 頻繁（每秒好幾次） 配置速率太高
STW 時間長（> 5 ms） goroutine 太多、堆疊太大、或有超大物件
GC CPU 比例高（> 15%） 配置速率太高，或存活集太大
記憶體只增不減 洩漏，不是 GC 問題

第二步：減少配置（最有效）#

go test -bench=. -memprofile=mem.out
go tool pprof -sample_index=alloc_space -http=:8081 mem.out

找出配置量最大的幾個地方，用 記憶體配置器 那節的清單處理。

這幾乎總是收益最大的一步。 調參數只是把問題往後推，減少配置才是根治。

第三步：才調參數#

# 記憶體充裕、想降低 GC CPU
GOGC=200

# 容器環境、要避免 OOM
GOMEMLIMIT=450MiB

# 短命的 CLI 工具
GOGC=off

第四步：考慮架構層面#

  • 物件池化 —— sync.Pool 處理高頻的大物件
  • 索引取代指標 —— []Node + int32 取代 *Node，消除寫入屏障與掃描成本
  • 值型別取代指標型別 —— []Item 而非 []*Item
  • unsafe 手動管理 —— 極端情況才考慮，風險很高

正式環境的六個典型問題#

前面的調校流程是通則。這一節換成症狀導向——你在監控上看到什麼、代表什麼、該怎麼辦。

症狀 最可能的原因 先做什麼
容器被 OOMKilled，但 HeapAlloc 看起來很低 GC 目標超過容器上限 設 GOMEMLIMIT
RSS 一直不降，看起來像洩漏 HeapIdle 沒歸還，不是洩漏 比對 HeapReleased
存活集持續成長 真的洩漏 heap 剖析看 inuse_space
GC 每秒好幾次、CPU 佔比高 配置速率太高 heap 剖析看 alloc_space
CPU 幾乎全在 GC、服務停擺 GC 死亡螺旋 放寬 GOMEMLIMIT 或降存活集
STW 從幾十微秒漲到數毫秒 goroutine 太多、堆疊總量大 看 gctrace 的 MB stacks

① 容器被 OOMKilled，但堆積看起來很小#

這是最常見也最容易誤診的一個。典型情境：

容器 limit:     512 MiB
HeapAlloc:      約 200 MiB
結果:           Pod 被 OOMKilled

原因：GOGC=100 的意思是「堆積長到存活量的兩倍才 GC」。存活量 200 MiB → GC 目標 400 MiB → 加上 goroutine 堆疊、runtime 結構、執行檔本身，RSS 輕鬆超過 512 MiB。

Go runtime 完全不知道容器的記憶體上限（CPU 上限在 1.25 之後知道了，記憶體則從來不會自動偵測）。

解法：

GOMEMLIMIT=440MiB ./app

或在程式裡：

import "runtime/debug"

func init() {
    debug.SetMemoryLimit(440 << 20)
}

留 10–15% 給非堆積用量。如果用 Kubernetes，可以直接從 limit 推導：

env:
  - name: GOMEMLIMIT
    valueFrom:
      resourceFieldRef:
        resource: limits.memory
        divisor: 1
  # 注意：這樣拿到的是 100% 的 limit，實務上建議另外算成 85–90%

GOMEMLIMIT 涵蓋的範圍

它管的是 Go runtime 管理的記憶體總量（堆積 + 堆疊 + runtime 內部結構），不含：

  • cgo 配置的記憶體
  • 執行檔與共享函式庫的映射
  • 作業系統的檔案快取

所以有用 cgo 的服務要留更多餘裕。

② RSS 不降：那不是洩漏#

package main

import (
    "fmt"
    "runtime"
)

func snapshot(label string) {
    var m runtime.MemStats
    runtime.ReadMemStats(&m)
    fmt.Printf("%-10s HeapAlloc=%4d MB  HeapIdle=%4d MB  HeapReleased=%4d MB\n",
        label, m.HeapAlloc>>20, m.HeapIdle>>20, m.HeapReleased>>20)
}

func main() {
    snapshot("啟動")

    data := make([][]byte, 200)
    for i := range data {
        data[i] = make([]byte, 1<<20) // 共 200 MB
    }
    snapshot("配置後")

    data = nil
    runtime.GC()
    snapshot("GC 後") // HeapAlloc 掉了，但 HeapIdle 很高
}

判斷準則：

  • HeapAlloc 下降但 HeapIdle 很高 → 記憶體被 Go 佔著沒還給 OS，不是洩漏。scavenger 會漸進歸還。
  • HeapAlloc 持續成長 → 真的洩漏，去做 heap 剖析。

急著要 RSS 下降（例如批次任務跑完）可以：

import "runtime/debug"

debug.FreeOSMemory() // 強制 GC + 盡量歸還

但它會觸發一次完整的 STW GC，絕不要放在請求路徑或定時任務裡。

③ GC 太頻繁#

gctrace 上看到每秒好幾次 GC、GCCPUFraction 超過 10%：

go tool pprof -sample_index=alloc_space -http=:8081 http://localhost:6060/debug/pprof/allocs

注意是 alloc_space 不是 inuse_space——前者是「總共配置了多少」（GC 壓力來源），後者是「現在還活著多少」（洩漏來源）。這兩個常常指向完全不同的地方。

找到熱點後，優先順序是：減少配置 → 提高 GOGC → 其他。詳見減少配置的實用清單。

④ GC 死亡螺旋#

症狀非常明顯：CPU 幾乎 100% 都在 GC，服務等同停擺，但沒有崩潰。

成因是 GOMEMLIMIT 設得比「存活集本身」還小。runtime 為了守住上限會不斷觸發 GC，但每次都回收不到東西——因為那些記憶體真的還在用。

存活集:        450 MiB
GOMEMLIMIT:    400 MiB
→ 永遠達不到目標 → 連續 GC → CPU 被吃光

GOMEMLIMIT 是軟性上限，Go 不會為了守住它而殺掉你的程式，只會一直嘗試。

診斷：gctrace 的 GC 編號快速跳動、GCCPUFraction 逼近 1.0。

解法：放寬上限、降低存活集（真正的修法），或加一個保險絲——

import "runtime/debug"

// Go 1.19+：設定一個底線，避免完全失控
debug.SetGCPercent(50) // 搭配 GOMEMLIMIT 使用

根治還是要讓存活集降下來。GOMEMLIMIT 不能拿來當「記憶體不夠」的解方，它只能防止「配置太快導致超標」。

⑤ STW 變長#

Go GC 的設計目標是 STW 不隨堆積大小成長。如果你看到 STW 從幾十微秒漲到數毫秒，堆積大小通常不是原因：

gc 42 @120.5s 4%: 0.03+18+2.1 ms clock, ..., 890 MB stacks, ...
                            ^^^                ^^^^^^^^^^^^
                            第三段 STW 變長      goroutine 堆疊總量

MB stacks 是關鍵。STW 階段要掃描所有 goroutine 的堆疊，goroutine 數量或堆疊大小失控就會拉長它。

// 監控 goroutine 數量 —— 最便宜的預警
runtime.NumGoroutine()

常見成因：goroutine 洩漏（見 channel）、或深遞迴讓個別堆疊長得很大（見 堆疊記憶體管理）。

⑥ 指標密集的資料結構#

如果你有一棵常變動的樹或圖，GC 期間效能會明顯掉。原因有兩個：每次指標寫入都要走寫入屏障，而且掃描要一個一個追指標。

// ✗ 每個節點一次配置，掃描要追 N 次指標
type Node struct {
    Value    int
    Children []*Node
}

// ✓ 用索引取代指標
type Node struct {
    Value    int
    Children []int32 // 索引，不是指標
}

type Tree struct {
    nodes []Node // 一整塊連續記憶體
}

func (t *Tree) Child(n *Node, i int) *Node {
    return &t.nodes[n.Children[i]]
}

改成索引之後：

  • 寫入屏障消失——int32 不是指標
  • GC 掃描變快——如果 []Node 整體不含指標，GC 可以直接跳過整塊
  • 快取友善——節點連續存放

代價是失去型別安全（索引可能越界或指向錯誤的節點），所以只在量測確認 GC 是瓶頸之後才做這種改寫。

常見誤解#

「GC 會壓縮記憶體、消除碎片。」 Go 的 GC 不搬移物件。碎片靠 size class 機制減輕，但不會被消除。

「呼叫 runtime.GC() 可以優化效能。」 相反。它會強制一次完整的 STW GC，通常讓事情更糟。只在基準測試裡建立乾淨起點時才用。

「記憶體用完就 OOM，跟 GC 無關。」 有關。GC 太晚觸發是容器 OOM 的常見原因，這正是 GOMEMLIMIT 要解決的問題。

「HeapAlloc 就是我的程式用了多少記憶體。」 不是。作業系統看到的 RSS 包含 HeapIdle（Go 取得但沒用的部分）、goroutine 堆疊、runtime 結構。RSS 通常比 HeapAlloc 大不少。

「GC 停頓會隨堆積變大而變長。」 標記總時間會，但 STW 時間不會（那是 Go GC 的核心設計目標）。堆積 100 GB 的服務，STW 仍應維持在數百微秒。
